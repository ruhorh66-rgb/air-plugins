# air-worker — исполнитель тяжёлых нероевых задач

Код контура едет через рой ruflo. Тяжёлая НЕроевая работа рою не нужна, а в сессию
оркестратора не помещается. Схема та же (`AIR_VIBECODING.md` § «Схема исполнения»):
оркестратор → отцеплённый процесс → подтверждение ЛПР кнопкой → сводка. Меняется
только то, ЧТО запускается по нажатию.

## Порядок

```text
1. python worker.py types                      какие типы задач подключены
2. python worker.py lock                       свободен ли канал бота (ОБЯЗАТЕЛЬНО до create)
3. python worker.py create <тип> <файл> --param k=v [--title ...]
4. python listener.py --once 30                ждать нажатия ЛПР и отработать
5. python worker.py status <id>                исход; python protocol.py — где ушло время
```

Скрипты — `skills/run-worker-task/scripts/`. Рантайм (база, замок, результаты,
протокол) — `E:\-4-\air-worker`, вне git.

## Чего этот канал не делает — и это не настройка

Границы взяты у `air-ruflo-bridge` и ослаблены быть не могут: они условие, при
котором Telegram-канал вообще допустим, а не параметр.

- **текст из чата командой не становится.** Читается только `callback_data` вида
  `awrun:<id>` / `awno:<id>`. Что запустится — решено В МОМЕНТ СОЗДАНИЯ заявки:
  подписанное поле `task_type` выбирает исполнителя из `executors.REGISTRY`;
- **нажатие с чужого chat_id игнорируется молча** — ответ подтвердил бы, что канал
  существует;
- **подпись проверяется в момент нажатия**, а не создания: между кнопкой и нажатием
  проходят часы. Не сошлась подпись или изменился сам материал — заявка мертва,
  а не «запустим осторожно»;
- **заявка одноразовая и с TTL.**

## Один бот на двоих — и почему это лок, а не вежливость

Бот `air-comms-telegram-bot` общий с `air-ruflo-bridge`. Long polling у Telegram
эксклюзивен по факту: апдейт достаётся тому, кто спросил первым. 10.08.2026 кнопка
air-worker досталась слушателю ruflo, и тот ответил «Заявка не найдена».

Поэтому проверяются ДВА замка, и `create` отказывается работать, пока чужой
слушатель жив:

```text
own_listener        held / free / unknown   свой замок E:\-4-\air-worker\listener.lock.json
bot_channel_foreign held / free / unknown   чужой процесс approve_listener.py
```

**`unknown` НИКОГДА не равен `free`.** Непрочитанный замок и неудавшийся опрос
процессов — это «не знаю», и в вопросе исполнения «не знаю» равносильно «занято».

## Типы задач

| Тип | Состояние | Приватность |
|---|---|---|
| `openrouter-llm` | подключён (через llm-queue) | материал уходит внешней модели — **только уровень 0** |
| `qwen-local` | подключён (через llm-queue) | материал не покидает машину — уровень 1 |

Второй тип добавляется строкой в `executors.REGISTRY`: ядро, подпись, лок и
слушатель при этом не трогаются. Имя модели без `/` в `openrouter-llm` отвергается —
роутер отправил бы такой запрос в llama молча, а молчаливая подмена бэкенда хуже
отказа.

**Исполнение — через `llm-queue` (TASK-OBS-0054, 2в), не свой subprocess/сеть.**
Оба исполнителя в `executors.py` только ставят задание в очередь
(`dispatcher.py enqueue`/`enqueue-exec` + `run` + `show`) и забирают результат —
фактический HTTP-вызов делает подпроцесс, которым управляет llm-queue (слот,
ретрай, переживание перезапуска). `qwen-local` идёт через `enqueue` (LLM-пул,
llama-server порт 8080); `openrouter-llm` — через `enqueue-exec` (cpu-пул: LLM-пул
зашит на локальную qwen и не даёт выбрать бэкенд). Внешний ход у `openrouter-llm`
— только через локальный `E:\-4-\codex-shim\air_llm_router.py`. Своего ключа
OpenRouter плагин не держит; free-only guard роутера остаётся единственным местом,
где решается вопрос платности.

## Цикл

```text
цель   — заявка отработала, и её результат получен ИМЕННО по подтверждённому материалу
гейт   — python selftest.py (19 проверок + protocol selfcheck; провал = 1)
         + python worker.py lock (can_listen=false → не начинать вовсе)
предел — 2 круга: несошедшаяся подпись чинится не повтором, а новой заявкой
показ  — один итог: id, тип, модель, счётчики, путь результата
```

**`unknown` у замка — не «чисто».** Неудачный опрос процессов даёт третий исход, и
цикл на нём не закрывается.

## Секреты

Windows keyring, сервис `air-comms-telegram-bot`: `botfather-token`, `chat_id`,
`request-hmac-key`. Своего бота и второй записи под тот же секрет плагин не заводит
(`NEW_PLUGIN_CHECKLIST.md` § 6). Ключ подписи заводит только создающая сторона;
проверяющая — никогда, иначе удаление ключа стало бы способом обойти проверку.

## Что в логи не попадает

Содержимое обрабатываемого материала — никогда: пути, хэши, счётчики, коды. Правило
исполняется механически (`protocol._scrub` режет не-скаляры и строки длиннее 200
знаков), а не дисциплиной вызывающего кода.

## Доставка правки — три шага, не два

```text
1. поднять version в .claude-plugin/plugin.json
2. пересобрать копию в кэше маркетплейса
3. claude plugin update air-worker@air-plugins
```

Третий обязателен: бамп сам по себе плагин не переустанавливает (`ERR-2026-000203`).
Версия не поднимается, пока ЛПР не сказал «беру».

## Лестница исполнителей (TASK-OBS-0054)

`scripts/ladder.py` + `scripts/ladder_priors.json` — шесть ступеней для
однотипной проверочной работы (пилот: волт ЦКБА), поверх того же гейта:
кнопка ЛПР авторизует ПАЧКУ (2д), лестница внутри пачки шагает по заявкам
сама.

```text
0 script $0 · 1 qwen-local $0 (llm-queue) · 2 openrouter-free ~0 (llm-queue)
3 codex вне квоты (llm-queue) · 4 haiku/sonnet ×0,04/×0,2 · 5 opus ×1
```

- **`escalate(claim, level, reason)`** — `reason` обязателен; без него —
  исключение. Молчаливый подъём запрещён (2а): это дефект, из-за которого у
  роя было 88 % Opus.
- **Уровни 1–3 исполняет `llm-queue`**, не свой `subprocess`: `ladder.py`
  зовёт документированный CLI `dispatcher.py` (`enqueue` / `enqueue-exec` /
  `run` / `show`). Уровни 4–5 — суждение Claude: `ladder.py` их не исполняет
  (это не CPU-процесс), а отдаёт оркестратору конверт
  (`pending_orchestrator: True`) для вызова через Task/Agent.
- **`choose_start_level(card_type, volume, priors=…)`** — старт ВСЕГДА 0,
  пока `ladder_priors.json` пуст (файл по умолчанию — `[]`). Приор может
  сместить старт вверх только при накопленной статистике (≥5 исходов,
  успех уровня 0 < 15 %) и объёме партии ≥3 — разовую заявку не оптимизируем.
- **`verify(card_type, claim, evidence)`** — по одному проверяльщику на
  четыре типа (2б): `chronology` (дата/номер/предмет/стороны),
  `decision`/`task` (документ назван · существует · предмет решения в нём
  есть), `principle`/`pattern` (цитата дословно в источнике), `risk`/`fork`/
  прочее (сумма и состав сходятся с расчётом). Проверка не прошла — заявка
  идёт на следующую ступень, а не закрывается.
- **`update_priors(card_type, level, passed)`** — после закрытой заявки, не
  по запросу совета (2г). Без блокировки файла (`ponytail:` в коде) —
  апгрейд при параллелизме выше пилотных ~100 заявок.

Проверка: `python ladder.py` (assert-самотест, офлайн, без обращения к
`llm-queue`).

**Границы, не переступленные этим модулем**: реальные CSV-реестры волта ЦКБА
(`source_verification_queue*.csv`) он не открывает и не пишет — `claim` и
`evidence` здесь абстрактные словари, привязка к реестрам ЦКБА отдельной
работой; ключ OpenRouter не читает — level2 зовёт уже существующий локальный
роутер с его free-only guard; `llm-queue`/`dispatcher.py` не правится —
только вызывается его CLI.

**Не хватает в интерфейсе `llm-queue`** (не правится здесь, названо для
отдельного решения):
1. `enqueue` (LLM-пул) жёстко зашит на локальную модель
   (`llm_client.MODEL_NAME = qwen2.5-7b-instruct`) — нет параметра
   бэкенда/модели, поэтому уровни 2–3 вынуждены идти через `enqueue-exec`
   (cpu-пул), рассчитанный на CPU-насыщающие процессы, а не на сетевые
   API-вызовы.
2. Нет команды «поставить и дождаться именно этого job»: `run --limit 1`
   берёт самое старое/приоритетное задание в очереди — при параллельных
   заявках (2д) чужой job может обработаться раньше своего.
