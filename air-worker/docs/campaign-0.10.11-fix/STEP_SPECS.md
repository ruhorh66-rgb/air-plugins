# Спецификации шагов кампании 0.10.11-fix

Общее для всех шагов:
- Работать только в каталоге `cmd/` (Go, модуль `airos/air-worker`) и только над своим шагом. Не менять `PLAN.md`, `run-config.json`, `goal/`, `docs/`, `tools/`, манифесты и бинарники.
- Не менять и не ослаблять существующие тесты; новые тесты называть ровно так, как названо в шаге (судья ищет тест по имени, `-run ^Имя$`).
- Кодировка UTF-8, переводы строк LF. Комментарии в коде — по-русски, коротко, как вокруг.
- Проверка: `go -C cmd test ./... -count=1` и `go -C cmd vet ./...` должны остаться зелёными. Если запустить go не удаётся — не выдумывать результат, назвать это в ответе.
- Сеть, настоящие `codex` и `claude` в тестах не звать. Тесты без побочных эффектов вне `t.TempDir()`.
- Без новых зависимостей. Кратчайший работающий код; никаких абстракций сверх нужного.

## Д-1а. Повтор `os.Rename` в `writeFileAtomic` (Windows)

Файл `cmd/lock_windows.go`, функция `writeFileAtomic`. Сейчас: `os.WriteFile(tmp)` и `os.Rename(tmp, path)` без повтора. На Windows `Rename` поверх файла, который в этот момент открыт другим процессом без `FILE_SHARE_DELETE` (так открывает `os.ReadFile`), падает с `ERROR_ACCESS_DENIED` (5), `ERROR_SHARING_VIOLATION` (32) или `ERROR_LOCK_VIOLATION` (33).

Сделать: повторять `os.Rename` при этих трёх ошибках с короткой паузой (10 мс, удваивая до 100 мс), пока не пройдёт 2 секунды суммарно; другие ошибки возвращать сразу; после исчерпания времени убрать `tmp` и вернуть последнюю ошибку. Время ожидания и паузу вынести в переменные пакета, чтобы тест мог их уменьшить. `cmd/lock_other.go` не менять.

Тест `TestWriteFileAtomicRetriesRenameWhileReaderHoldsTarget` (только Windows, иначе `t.Skip`), в `cmd/lock_windows_test.go`: создать целевой файл в `t.TempDir()`; открыть его `os.Open` и держать; в горутине закрыть через 300 мс; вызвать `writeFileAtomic` с новым содержимым; ожидать `nil` и новое содержимое. Второй случай: читатель держит дольше уменьшенного времени ожидания — ожидать ошибку, `tmp`-файла в каталоге не остаётся.

## Д-1б. Ошибка регистрации PID не глотается

Файл `cmd/job_receipt.go`, функция `runReceiptedWithMeta`. Сейчас после `cmd.Start()` запись `r.PID = cmd.Process.Pid; r.ProcessStarted = true; _ = writeJobReceipt(receiptPath, r)` игнорирует ошибку: квитанция остаётся с PID заглушки и `process_started=false`, а процесс работает невидимым для `adapter status`.

Сделать: ошибку записи проверять. При ошибке — завершить дочерний процесс (`cmd.Process.Kill()`, затем дождаться `cmd.Wait()`), закрыть `outFile`, записать `FAILED` (по возможности, ошибку этой записи не скрывать, но и не терять основную), освободить замок и вернуть ошибку с текстом `не удалось зарегистрировать PID …`. Запуск без зарегистрированного PID не считается запущенным.

Шов для теста: запись квитанции вызывать через переменную пакета (`var writeJobReceiptFunc = writeJobReceipt` или равноценное) и использовать её и в `startJobReceipt`, и в `runReceiptedWithMeta`, и в `finishJobReceipt`.

Тест `TestRunReceiptedFailsClosedWhenPIDRegistrationFails` в `cmd/job_receipt_test.go` (или рядом с существующими тестами квитанций): подменить шов так, чтобы запись падала начиная с записи после `Start`; запустить долгую команду (например, `powershell.exe -NoProfile -Command Start-Sleep 30`; на не-Windows — `sleep 30`); ожидать ошибку, что процесс уже не жив (по PID из `cmd.Process`), что квитанция не осталась `RUNNING` с живым PID. Тест не должен ждать 30 секунд.

## Д-2. Читатель реестра принимает `facts` как `items`

Файл `cmd/judge.go`, тип `checklistFile` (`Items []factItem json:"items"`). Реестр, записанный под ключом `facts`, читается как пустой, и `goals`/`judge` отвечают «факта нет в реестре».

Сделать: принимать оба ключа. Если есть `items` — они главные; если `items` нет (или пуст) — брать `facts`; если есть оба — объединить, при совпадении `id` побеждает `items`. Остальные поля записи (`fact`, `proved_by`, `evidence`) на разбор не влияют. Изменение только в разборе реестра; место чтения в судье остаётся одним.

Тест `TestChecklistAcceptsFactsKeyAsItems` в `cmd/judge_test.go` (или рядом): реестр только с `facts` даёт те же факты и статусы, что такой же с `items`; реестр с обоими ключами — объединение; пустой реестр — пусто без ошибки.

## Д-5. Закрытие модельного шага принадлежит ядру; план вне записи исполнителя

Файлы: `cmd/loop.go` (вокруг вызова `c.runModelStep` и после вердиктов судей), `cmd/runner.go` (текст задания исполнителю), при необходимости `cmd/planfile.go`.

Сейчас: `runner.go` велит исполнителю зачеркнуть номер шага и «снять зачёркивание, если критерий не выполнен»; ядро строку не возвращает (`shouldAdvance` лишь не засчитывает закрытие). Живые случаи ASW 21.09: Codex вычеркнул и переписал строку 30, смысловой судья вернул NOT_PROVEN, а строка осталась закрытой; во втором случае судья не ответил (лимит), а исполнитель всё равно вычеркнул строку. Значит, дело в праве записи в план, а не только в вердикте.

Сделать:
1. Снимок: перед `c.runModelStep` прочитать байты плана (`before`).
2. После хода исполнителя, до судей: если байты плана изменились, вернуть их побайтно функцией `restorePlanBytes(path string, before []byte) error` (имя и сигнатура обязательны, мутационная проверка правит её тело), напечатать `  правка PLAN.md исполнителем отклонена: план возвращён к состоянию до хода` и отметить в записи журнала шага (`plan_tamper: true`). Относится ко всем модельным ступеням, в том числе ведущей и субагентам оркестрации.
3. После вердиктов судей: строку закрывает ядро функцией `closeModelStepOnPass(path string, step workStep) error` (имя и сигнатура обязательны; внутри вызывает `closeStepInPlan`) только если фактический вердикт по критериям шага пройден и смысловой судья вернул PASS, `step_done: yes`, без ошибки (если смысловой судья для этого исполнителя не вызывается — достаточно фактического). При любом другом исходе (NOT_PROVEN, DRIFT, ошибка или молчание судьи, красный критерий) в плане ничего не менять.
4. Задание исполнителю (`runner.go`): убрать требование зачёркивать номер и «снять зачёркивание»; вместо этого — «Не правь PLAN.md: шаг закрывает ядро по вердикту судей, правка плана отклоняется». Соседние строки привести в соответствие.
5. Ступень `script` не менять: строку закрывает петля по коду команды (К31).

Тесты (в `cmd/planclose_test.go`; выделить проверяемую функцию, например `reconcileModelStepPlan(planPath string, before []byte, step workStep, factualPass bool, sem *semanticRun) (closed, tampered bool, err error)`, чтобы тест не гонял живую петлю; петля вызывает её):

- `TestExecutorCannotModifyPlan`: исполнитель изменил план любым способом (и чужие строки); при PASS итог — `before` плюс закрытая ядром строка шага, чужих правок нет.
- `TestEngineClosesModelStepOnPass`: исполнитель план не менял, вердикт PASS — строка закрыта ядром так же, как `closeStepInPlan`.
- `TestExecutorPromptDoesNotAskToCloseTheRow`: собранное задание не содержит «Зачеркни номер» и «сними зачёркивание» и содержит «Не правь PLAN.md».

Ограничение: песочница `workspace-write` не даёт запретить запись в один файл, поэтому защита — откат после хода, а не запрет записи.
