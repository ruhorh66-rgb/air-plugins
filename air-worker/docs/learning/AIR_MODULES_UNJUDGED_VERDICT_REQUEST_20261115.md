# Заявка в air-modules · вердикт «unjudged / judge not configured» · 15.11.2026

Исполнитель: Dev Work 35. Решение куратора 15.11.2026: в А1 не трогаем, в А3
закрываем выводом CLI; вариант правки air-modules — заявкой, без кода.

## Факт

`github.com/ruhorh66-rgb/air-modules` v0.1.1, `learning/journal.go`, `observe`:
на каждое событие `kind=run_completed` при `Config.Judge == nil` пишется строка
`air.learning.verdict/v1` со `status=unjudged`, `reason="judge not configured"`,
затем вызывается `reviewEvent`. В рантайме AirWorker на 15.11.2026: 1527 таких
вердиктов на 1531 событие. Стоп-хук AirWorker (`sharedLearningStop`) и захват
отказов CLI оба пишут `run_completed`, поэтому вердикт приходит к каждому ходу.

## Что не так

Строка вердикта не несёт наблюдения: это свойство конфигурации, а не исхода хода.
Ревьюер получает её как вход и выводит из неё процедуры «судья не настроен —
считать прогон неоценённым» — 32 дубля одного класса в каталоге.

## Варианты (на решение владельца air-modules)

1. Не писать вердикт при `Judge == nil`; отсутствие вердикта и есть «не оценено».
   Потребители, читающие вердикт после `run_completed`, должны принимать его
   отсутствие (проверить `judge`, `review`, отчёты).
2. Писать один раз на конфигурацию (статус модуля), а не на событие.
3. Оставить строку, но помечать `informational: true`, и не передавать такие
   вердикты ревьюеру как материал урока.

Рекомендация исполнителя: вариант 1 или 3; оба требуют минорной версии
air-modules и проверки совместимости потребителей (AirWorker и другие продукты
на общем модуле). До решения AirWorker закрывает видимую часть в А3: CLI сам
печатает «судья не настроен → прогон не оценён», навык для этого не нужен.
