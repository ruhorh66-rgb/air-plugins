# Граница: где кончается Go и начинается Python

Решение 13.09.2026. Записано потому, что вопрос ЛПР «а как бинарник взаимодействует с
ЛЛМ» вскрыл не дефект, а неназванную границу: взаимодействие с моделью живёт в двух
местах, и пока это не объявлено, каждый следующий читатель считает по-своему.

## Две стороны и что каждая держит

| | Go, `bin/air-worker.exe` | Python, `skills/run-worker-task/scripts/` |
|---|---|---|
| Что это | **механизм** — как задача доводится до результата | **исполнение** — что именно делается |
| Роли | цель, судья, двигатель, петля, планировщик | лестница из шести ступеней, подписанная заявка, протокол, метрики |
| Чем ходит к модели | внешние runner CLI (`claude`, `codex`, `opencode`); для Router вызывает штатный AirLLMRouter bridge, но не выбирает provider/ключ | `llm-queue` своим объявленным CLI для legacy skill-path |
| Что знает о деньгах | потолок прогона и бюджет кампании | расход по ступеням, free-only guard |
| Чего НЕ делает | не реализует очередь, не хранит provider-ключи и не ходит прямо в provider API | не знает про план, вердикт, расстояние до цели |

## Почему бинарник не самодостаточен и не станет

Лестница исполнения задач ходит через **`llm-queue` — соседний продукт того же
маркетплейса**, у которого свой документированный CLI (`enqueue`, `enqueue-exec`, `run`,
`show`). Контракт `ladder.py` объявляет это прямо: «`llm-queue` не переписан: всё
исполнение уровней 1-3 идёт ЕГО документированным CLI, внутрь `dispatcher.py`/
`llm_client.py` этот файл не лезет».

Сделать бинарник самодостаточным в смысле **переписать очередь/provider policy** значит завести
в нём второй `dispatcher`/`llm_client`, provider key или прямой provider API. Это запрещено.
Начиная с 0.10.5 бинарник при этом умеет запускать внешний OpenCode runner и AirLLMRouter
bridge: процессом и receipt владеет AirWorker, а provider/model/key policy остаётся у внешнего
инструмента. Само имя `AIR_LLM_ROUTER_PY` поэтому не является нарушением границы.

Граница проведена по владению политикой и очередью, а не по имени запускаемого CLI. Python
legacy skill-path остаётся допустимым потребителем `llm-queue`; Go не дублирует её реализацию.

## Точки входа: их две, и они разной природы

**Сессия зовёт продукт скилом.** Плагин делает `run-worker-task` видимым; скил создаёт
подписанную заявку и немедленно исполняет её через очередь. Это путь для работы.

**Человек и механизм зовут бинарник.** `air-worker judge | drift | loop | plan | tool` —
путь для управления: спросить вердикт, замерить расстояние, прокрутить план, разбить цель,
узнать исполнителя. Денег не тратит ничего, кроме `loop` и `plan`.

Плагин нужен обеим: первой — чтобы скил был виден сессии, второй — чтобы страж режима
приехал вместе с продуктом. Установка плагина и есть объявление обеих точек входа.

## Что эта граница запрещает

1. **Go не заводит своего клиента очереди.** Нужен доступ к очереди — через скил.
2. **Python не заводит своего судьи, плана и расстояния до цели.** Нужен вердикт — через
   бинарник, `air-worker judge`.
3. **Ни одна сторона не дублирует то, что умеет другая.** Дубль не усиливает, а создаёт
   расхождение: это правило куплено сегодня трижды — на проверках, на путях и на
   реализациях судьи.

Проверяется `tools/check-boundary.ps1` каждым прогоном судьи.
