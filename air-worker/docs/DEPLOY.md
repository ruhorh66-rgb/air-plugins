# Развёртывание air-worker на второй машине

Написано 13.09.2026 по прямому запросу ЛПР: нужна сборка, которую разворачивают **без
повышения прав**.

Короткий ответ на главный вопрос: **повышение не требуется ни на одном шаге.** Всё, что
нужно, ставится в пользовательскую область или уже лежит в клоне репозитория.

## Что должно быть на машине заранее

| Что | Зачем | Повышение |
|---|---|---|
| Python 3.12+ | исполнитель и самотест | не требуется, если уже отвечает |
| `keyring` для этого Python | ключ подписи заявок | не требуется, `pip install --user keyring` |
| клон `air-plugins` | сам продукт | не требуется |
| PowerShell 5.1 | судья, петля, хуки | встроен в Windows |

**Чего НЕ нужно, вопреки ожиданию.** `git` нужен только чтобы получить клон; если клон уже
есть, он не нужен. `go` нужен только чтобы СОБРАТЬ бинарник — собранный лежит в
репозитории (`bin/air-worker.exe`) именно для этого. `node`, `gh`, `tesseract`, 7-Zip,
Total Commander продукту не нужны вовсе.

## Шаги

### 1. Обновить клон — повышение не требуется

```
git -C <клон air-plugins> pull
```

Клона нет и `git` недоступен — возьми архив ветки `main` любым способом, важно только
содержимое каталога `air-worker/`.

### 2. Объявить рантайм — повышение не требуется

Решение о томе принимает человек, механизм ничего не выбирает сам. Резолвер спрашивает в
таком порядке: `AIR_WORKER_RUNTIME`, затем `AIR_RUNTIME_ROOT`, затем
`%LOCALAPPDATA%\air-worker`.

Умолчание кладёт состояние **в профиль пользователя**, а профиль в периметр бэкапа контура
не входит. Поэтому на машинах контура рантайм объявляется явно, на защищённом томе:

```
setx AIR_WORKER_RUNTIME "R:\-4-\air-worker"
```

`setx` пишет в пользовательскую область реестра — повышения не требует. **Переменная
доходит только до процессов, запущенных ПОСЛЕ неё**: уже открытые оболочки её не увидят,
и это не поломка, а свойство Windows. Тот же класс стоил нам трёх ходов на токене 12.09.

### 3. Завести ключ подписи — повышение не требуется, но это решение ЛПР

Ключ подписи заявок **заводится на каждой машине свой и не переносится между машинами**.
Значения секретов между площадками через сессии не передаются — это стоячее правило
контура, и обхода у него нет.

Ключ создаётся сам при первом подписании (`hmac_key(create_if_missing=True)`) и ложится в
Windows keyring под учётной записью, которую называет код продукта. Отдельного действия
не нужно; если keyring на машине не настроен, значение подаётся через
`AIR_WORKER_HMAC_KEY` — тогда его источником распоряжается человек, а не мы.

### 4. Установить плагин в Claude Code — повышение не требуется

Плагины Claude Code живут в пользовательском каталоге настроек. Установка — это
регистрация маркетплейса и установка пакета из него; ни системного реестра, ни службы,
ни `Program Files` продукт не трогает.

Команды `/plugin` вводятся в интерактивном сеансе `claude`, и вводит их **человек**: это
изменение его настроек, а не наша работа. Порядок:

```
/plugin marketplace add <путь к клону air-plugins>
/plugin install air-worker@air-plugins
/plugin enable air-worker@air-plugins
```

**Третья команда обязательна, и без неё установка выглядит успешной.** Найдено
AIR-ENV-002 13.09.2026 на живой установке: `install` ставит плагин ВЫКЛЮЧЕННЫМ и говорит
об этом одной строкой, которую легко пропустить. Плагин при этом числится установленным,
а хуки не приходят — то есть страж режима отсутствует, и отсутствует молча. Ровно тот
класс, который эта инструкция и закрывает, только на шаг позже.

Выключенным по умолчанию плагин остаётся НАМЕРЕННО (`defaultEnabled: false` в манифесте):
он несёт хуки, которые не дают закончить ход без утверждённого формата. Механизм, который
начинает блокировать ходы от одной установки, снимут первым же движением и вместе с
пользой. Включение — отдельное осознанное действие человека.

Проверить, что хуки действительно приехали: `/plugin details air-worker@air-plugins` —
должно быть 5 хуков (Stop, UserPromptSubmit, SubagentStart, SubagentStop, PreToolUse).
Хуки читаются при СТАРТЕ сессии: включивший их сеанс их ещё не увидит, следующий увидит.

### 4a. Проверить канон плагина — до установки и после

```
powershell -NoProfile -ExecutionPolicy Bypass -File <клон>\air-worker\tools\check-plugin.ps1
```

Проверяет ПЕРЕНОСИМОСТЬ ОБЪЯВЛЕНИЙ, а не наличие файлов: абсолютный путь с буквой диска в
манифесте, `hooks/hooks.json` или frontmatter скила — отказ, даже если сегодня он
существует. Основание: до 13.09.2026 хуки были объявлены абсолютным путём машины
разработчика, и на любой другой машине плагин зарегистрировал бы их в пустоту — молча,
потому что несработавший обработчик неотличим от отсутствующего.

### 5. Проверить, что развернулось — прогоном, а не глазом

```
powershell -NoProfile -ExecutionPolicy Bypass -File <клон>\air-worker\tools\check-deploy.ps1
```

Требование к этой проверке поставила AIR-ENV-002, и оно здесь главное: **не «файлы на
месте», а прогон, отвечающий кодом.** Наличие каталога мы за один день восемь раз подряд
принимали за установленный пакет.

Что она запускает на самом деле:

1. Python — спрашивает версию, а не ищет файл (в `WindowsApps` лежат алиасы-заглушки,
   которые находятся и не исполняются);
2. `bin/air-worker.exe version` — отвечает ли бинарник;
3. судья продукта — **выносит ли он вердикт**; коды 0, 1 и 2 здесь одинаково хороши, плохо
   только отсутствие ответа;
4. самотест продукта — 36 проверок подписи, приватности, лестницы, протокола;
5. рантайм — разрешается и **пишется**; право записи проверяется записью, и отдельно
   говорится, если рантайм оказался в профиле;
6. ключ подписи — есть или нет. **Значение не читается и не печатается**: имена учётной
   записи проверка спрашивает у кода продукта, а не хранит своей копией.

Коды: `0` развернулось, `1` развернулось не полностью, `2` проверять нечем.

## Чего в этой инструкции сознательно нет

Переноса секретов между машинами; установки чего-либо в `Program Files`; задач планировщика
ОС — двигатель цели крутится одним запуском и будильника не требует (решение ЛПР
12.09.2026).
