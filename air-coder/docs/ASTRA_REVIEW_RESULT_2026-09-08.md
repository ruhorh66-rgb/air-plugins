# AirCoder — ревью работы Sol и план продолжения

Дата: 8 сентября 2026 года. Объект: `air-coder` в `ruhorh66-rgb/air-plugins`.

Проверенный HEAD: `eaf4b2e51bb7421ff29479ce3a24145f126a0f56`, ветка `ai/aircoder-ruflo-contract-beta3-20260907`. Версия продукта: `0.1.0-beta.3`, кандидат разработки. [Зафиксированный commit](https://github.com/ruhorh66-rgb/air-plugins/commit/eaf4b2e51bb7421ff29479ce3a24145f126a0f56).

**Решение ревью: продолжить эту реализацию после конкретных исправлений. Выпуск пока не принимать.** Sol сделал работающий путь через готовый исполнитель и две подтверждённые задачи. Однако восстановление запуска допускает обход независимой проверки изменений; пилот завершён лишь на 2 из 5 принятых задач. Доказательств выигрыша по всему процессу разработки пока недостаточно.

Ревью выполнено в режиме оркестрации: Luna проверила журналы через RDC, Terra — исполнитель и его тесты; оркестратор проверил выводы, маршрутизацию, метрики и итоговый план. Новые Codex/LLM-пилоты, изменения на сервере и операции выпуска не выполнялись. Локальные проверки использовали временные репозитории и заглушку исполнителя.

## 2. Замечания по коду

### R1 — P1: восстановление запуска пропускает проверку разрешённых и защищённых путей

`execute_one_turn()` сохраняет `executor_completed` до проверки diff. При первом запуске `gate_changed_paths()` вызывается внутри ветки `preflight_passed`. При `--resume` состояние `executor_completed` разрешено, но выполнение сразу переходит к acceptance; этот gate не вызывается. Окно существует и после ремонтного вызова. [Код: сохранение состояния, строки 489–524](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/run_coding_task.py#L489), [ветвление resume и acceptance, строки 601–655](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/run_coding_task.py#L601).

Воспроизведение: во временном Git-репозитории создан корректный контракт; смоделирована остановка после сохранения `executor_completed`; изменён защищённый файл `tests/protected.py`; вызван настоящий `run_task(..., resume=True)` с настоящими acceptance-командами. Вызов модели заблокирован заглушкой. Результат:

```json
{"exit_code":0,"status":"accepted","failure":null,"changed_paths":[],"acceptance":{"accepted":2,"total":2},"invoke_calls":0}
```

Это воспроизводимый ложный `accepted` на контрольном примере. Он не означает, что уже принятые 001/002 нарушили защиту; он опровергает общую гарантию защиты текущей версии.

**Исправление:** проверять актуальный diff после каждого завершённого исполнительного шага и при каждом продолжении, прежде чем запускать acceptance. Сохранённая отметка старой проверки не должна разрешать изменившийся с того времени diff. Перед финальным `accepted` повторно проверить границы, если acceptance-команды могут писать в репозиторий. Предпочтительно небольшое исправление существующей машины состояний.

**Приёмка:** resume с изменённым protected-путём → `blocked_protected`; с посторонним путём → `blocked_scope`; acceptance и исполнитель не запускаются. Корректный разрешённый diff проходит resume без второго вызова модели. Проверить первый исполнительный шаг и ремонтный шаг.

### R2 — P2: обязательный `git diff --check` не проверяет staged-изменения

Список изменённых путей учитывает index, а проверка качества diff выполняет только `git diff --check`. Добавленный через `git add` файл остаётся вне этой проверки. [Код, строка 265](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/run_coding_task.py#L262).

Локально staged-файл `app.py` с trailing whitespace прошёл обе команды runner; отдельный `git diff --cached --check` завершился кодом 2. Это конкретный пробел whitespace-проверки, а не доказательство провала всех тестов продукта.

**Исправление:** проверять рабочие и staged-изменения относительно согласованного базового состояния; для текущего контракта без commits исполнителя подходит `git diff HEAD --check` либо отдельные проверки обеих областей. Добавить один регрессионный сценарий со staged whitespace. Проверку новых untracked-файлов и границ изменений сохранить.

### R3 — P2: повторный resume перезаписывает длительность завершённой задачи

`run_task()` каждый раз задаёт новый `time.monotonic()`; даже для финального состояния пересобирает и сохраняет `result`. `build_result()` считает время только от этого нового старта. Повторный resume принятой задачи может заменить исходные минуты почти нулём. При реальном продолжении теряется время первого процесса. [Расчёт результата, строки 528–548](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/run_coding_task.py#L528), [перезапись финального результата, строки 620–626](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/run_coding_task.py#L620).

Локальная проверка расчёта: сохранённое `elapsed_min=12.34`, длительность повторного обращения 0.06 секунды → новый результат `0.001` минуты. Поэтому текущие receipts нельзя без оговорок использовать для ROI после resume.

**Исправление:** повторный запрос завершённой задачи возвращает исходный финальный результат; время хранится устойчиво между процессами. Раздельно учитывать активное выполнение, ожидание/прерывание и календарное время до результата. Счётчики попыток и расход по всем обращениям сохранять. Не выдавать `direct_cost_usd=null` за бесплатность; выбранную в контракте модель обозначать как конфигурацию, если фактическая модель не подтверждена событиями.

**Приёмка:** повторный resume финальной задачи не изменяет результат и не вызывает исполнитель; возобновлённая задача сохраняет время и попытки обоих процессов. Метрики не улучшаются от повторного чтения статуса.

### R4 — незакрытая интеграция перед AC-05: штатный selector сохраняет прежний путь

Чистый вызов `select_executor({})` возвращает `chatgpt_rdc`. Аналогично малые задачи с `conserve` идут туда, а крупные автоматически направляются в Ruflo. Это соответствует текущему SKILL, но ещё не закрепляет выбранный в AC-02 готовый исполнитель как рабочий путь обычной задачи. [Selector, строки 51–79](https://github.com/ruhorh66-rgb/air-plugins/blob/eaf4b2e51bb7421ff29479ce3a24145f126a0f56/air-coder/skills/route-coding-task/scripts/select_executor.py#L51).

Это незавершённая интеграция, а не основание переписывать уже работающий runner. RDC должен оставаться привычным каналом управления; кодирование подходящей задачи выполняет готовый исполнитель. Настроить selector и SKILL согласованно с этим решением, реальной доступностью и экономическими ограничениями. При отсутствии квоты — честный статус ожидания/недоступности, без скрытого перехода на платный API. Не вводить обязательный Ruflo только из-за размера задачи.

**Приёмка:** из обычного сообщения пользователя сессия сама формирует контракт и запускает выбранный готовый исполнитель; пользователю не приходится вручную выбирать маршрут, составлять JSON и проводить повторные тестовые проходы. Полученный diff, проверки и receipt соответствуют именно этому входу. Отдельный сервис-диспетчер для этого не требуется.

## 4. Краткие ответы на вопросы handoff Sol

1. **Архитектура AC-03 приемлема?** Да: готовый Codex плюс небольшой слой адаптации. Сохранить направление, исправить переходы состояния и проверки.
2. **Квота как infrastructure failure и automatic retry=0?** Да. Отдельно от дефекта продукта; все попытки остаются в журнале и экономике.
3. **003B/004B/005B пригодны?** Да, как заранее зафиксированные небольшие задачи с красными защищёнными проверками. Подготовка ещё не является выполнением. Не менять состав ради улучшения процента после результатов.
4. **Подготовленный live resume достаточен?** После R1 и фактического исполнения он соответствует минимальному требованию AC-04: продолжение после завершённого исполнительного шага без второго LLM-вызова. Это не демонстрация бесшовного восстановления посреди работающей модели. Для in-flight остаётся честная остановка `uncertain_inflight`, без автоматического дублирования.
5. **Что блокирует AC-05?** R1–R3, незавершённые пять задач и live resume, затем проверка штатного входа R4 и конкретный пакет выпуска. Известные дефекты `task_id` при resume и внутренних `limits` уже отражены в подготовленных задачах; их также нужно закрыть, не выдавая за новые находки ревью.

## 5. Исполнимый план для следующей сессии Sol

### Шаг 1. Сохранить контрольную точку и подготовить короткий пакет исправлений

Принять это ревью относительно указанного SHA. Сверить HEAD/ветку и собственные незакоммиченные изменения, сохранить исходные receipts. Следующий scope — AirCoder и его тесты/документация; продуктивные Storage, Router, AIRVR и бизнес-продукты в него не входят. Применить действующие разрешения AIR_OS к конкретному пакету; уже разрешённые обратимые действия выполнять без повторных общих согласований. Это ревью само не снимает отдельный release gate.

### Шаг 2. Исправить R1–R3 без платных пилотных прогонов

Сначала добавить короткие регрессии на установленные дефекты, затем исправить существующий runner. Простые изменения поручить доступному экономному исполнителю; дорогой координатор нужен для проверки решения. Один связный пакет и один релевантный регрессионный прогон после исправлений. Повторять тесты только по конкретному сбою или обязательному gate, а не проводить несколько одинаковых циклов ради отчёта.

Зафиксировать ревизию исправленного runner отдельно от HEAD целевого репозитория каждой пилотной задачи. Проверять пилоты этим runner. Не переносить исправления целевых дефектов в красные ветки до исполнения задач: иначе исчезает предмет пилота. Если нужно перенести ветку, записать новый baseline и подтвердить, что её защищённая проверка по-прежнему падает по целевому дефекту.

### Шаг 3. Завершить AC-04 на существующем реестре

После локальных исправлений и проверки доступности выполнить последовательно 003B, 004B, 005B. Не перезапускать уже принятые 001/002 через модель только ради нового отчёта; необходимую проверку совместимости выполнять сохранёнными diff и независимыми тестами. При usage limit сохранить состояние, прекратить автоматические обращения и сообщить конкретный блокер. Не маскировать доступность модели дополнительными платными smoke-запросами.

Провести один подготовленный live interruption/resume исправленным runner: завершить один исполнительный шаг, зафиксировать состояние, прервать только процесс этой изолированной задачи, восстановить новым процессом. Подтвердить отсутствие второго вызова модели, сохранность времени/attempts и обязательное прохождение diff/protected gate. Отдельная проверка механизма не повышает счётчик пяти задач.

Критерий исходного ТЗ сохранить: результаты по всем пяти задачам, минимум четыре приняты, минимум два продукта, все обязательные проверки принятой задачи успешны, false-ready=0 и фактический resume без необоснованного повторения. Нельзя остановиться на «4 из 4» и объявить требование пяти выполненным. Старые остановки по квоте остаются в истории и суммарных затратах.

### Шаг 4. Довести обычный вход и предъявить экономику

Закрыть R4 в selector/SKILL. По возможности провести одну из оставшихся задач уже через этот вход, чтобы не расходовать отдельный LLM-запуск на демонстрацию. Канал «чат → RDC → готовый исполнитель → проверенный результат» должен работать без ручного управления тестовыми итерациями со стороны пользователя.

В итоговой таблице показать: initial/final SHA целевого кода, SHA runner, заданную модель и доступные фактические данные, время выполнения и ожидания, attempts/repair, затраты или unknown, обязательные проверки, ручные возвраты пользователю, итог. Считать расход и неуспешных обращений. Не объявлять ROI на основании двух задач и не принимать рассказ о прежних 3–4 проходах за измеренную baseline. Если сравнимой истории нет, так и написать; это не требует откладывать техническую приёмку ради большого исследования.

Проверку Android выполнять в фактическом клиенте пользователя; CLI-пилот сам по себе её не заменяет. Голосовой режим считать отдельной проверкой доступности интерфейса, не обещать его автоматически после установки AirCoder.

### Шаг 5. Подготовить AC-05 и следующий полезный этап

Предъявить конкретный кандидат выпуска: SHA, результаты приёмки, перечень файлов/настроек, способ установки, проверку после установки и откат. Merge/tag/release/install — только по действующему разрешению для этого пакета. Не менять статус development на выпущенный по одному успешному пилоту.

После принятия AirCoder следующий ограниченный бизнес-результат — через него подготовить адаптацию готового Storage-решения: воспроизводимый каталог выбранного участка Яндекс Диска, поиск контрольных оригиналов, объяснимые пропуски и план перехода. Полную миграцию Storage/Router и Copilot в текущую сессию не добавлять. Собственный код предметных продуктов сохранить.

## 6. Формат следующего доклада Sol

```text
review_base: eaf4b2e51bb7421ff29479ce3a24145f126a0f56
candidate_head: <фактический SHA>
R1 / R2 / R3 / R4: closed | open + точное подтверждение

```
