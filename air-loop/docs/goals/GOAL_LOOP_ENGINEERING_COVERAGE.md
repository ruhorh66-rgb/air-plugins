## Сверка по компонентам

Модель видео — 6 компонентов: Automations, Git worktrees, Skills,
Plugins/connectors (MCP), Subagents (Maker-Checker), Memory.

| Компонент | Покрывает ли `air-loop` | Чем покрыт в контуре на самом деле |
|---|---|---|
| Automations (триггер + решение передать агенту) | Нет | Task Scheduler, `air-tasks:session-start-triage` |
| Git worktrees (изоляция параллельных агентов) | Нет | `air-ruflo-bridge`/hive-mind, `Agent(isolation: "worktree")` |
| Skills (инструкция по рутине) | Нет | конвенция `SKILL.md` в каждом плагине |
| Plugins/connectors (MCP) | Нет | весь MCP-слой контура |
| Subagents / Maker-Checker | Нет, и не должен | Модуль 4 §9.1 («проверяющий другой природы»), Codex-контролёр — отдельный, уже существующий механизм; `loop_run.py`'s docstring сам это оговаривает: «не заменяет контроль другой природы (Модуль 4): здесь самопроверка той же модели» |
| Memory (внешнее состояние процесса) | Частично | `--protocol .jsonl` — лог ПОПЫТОК гейта (круг/код/время), не общая память процесса; настоящий аналог — `tasks.csv`+`PLAN-<дата>.md`, `learning_store.py`/`runs.sqlite3` по плагинам |

`air-loop` по факту покрывает не компонент модели целиком, а конкретный
приём внутри «внутреннего цикла» — machine-checkable success criteria как
условие остановки (`--gate`, код возврата), что видео описывает в разделе
про контракт: «criteria that the machine can check». Это единственный
компонент, который `air-loop` реализует, и делает это буквально — гейт
решает годен/не годен, `loop_run.py` не судит о качестве сам (см. его же
docstring).

## Вывод — доработка НЕ нужна сейчас

Пять из шести компонентов модели видео `air-loop` сознательно не
реализует — они уже есть в контуре как отдельные механизмы (таблица выше),
построенные до этого видео и независимо от него. Расширять `air-loop`,
чтобы он «стал» полной моделью Loop Engineering, означало бы дублировать
уже работающее в другом месте — обратное тому, что просит Ядро п. 2.5.

**Один узкий, не срочный пункт на будущее.** Видео (и цитата Cherny:
«the budget that caps it») называет расход токенов/бюджета первым риском
loop-инженерии. `air-loop` считает КРУГИ (`--limit`) и таймаут круга
(`--timeout`), но не считает суммарный токен-бюджет через круги. Сейчас
это не пробел на практике: единственная реальная интеграция —
`air-watch/scripts/gate.py`, детерминированный Python-скрипт (проверка
файлов/реестра), не вызов LLM внутри круга — тратить бюджет там нечему.
Актуализируется, если/когда какой-то `--gate` станет оборачивать вызов
агента, а не проверочный скрипт — тогда стоит добавить необязательный
параметр вроде `--budget-total`, по образцу уже существующего `budget`
в `Workflow`-скриптах (`budget.total`/`spent()`/`remaining()`), а не
изобретать заново.

## Это ещё не решение

Файл не меняет код `air-loop`, не заводит задачу на доработку и не выбирает
приоритет. Предметный ответ на вопрос ЛПР «нужна ли доработка» — да, вот он
(нет, не нужна, с одним названным условием, при котором пересмотреть). Если
и когда пункт про бюджет станет актуальным — решение сводить его в план
(и заводить ли `air-loop/docs/GOAL.md` вообще) остаётся за ЛПР.
