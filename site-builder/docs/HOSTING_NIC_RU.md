# Выкладка сайта на хостинг Руцентра (nic.ru)

Рабочая инструкция, собранная 09–10.09.2026 при публикации koord.pro и
tech-77.ru. Каждое утверждение здесь проверено на живом сервере, а не взято
из описания тарифа. Места, где легко потерять часы, отмечены отдельно.

---

## 1. Что за площадка

Тариф линейки **«Сайт-1 / Сайт-2 / Сайт-3»** — обычный виртуальный хостинг:
Apache за фронтальным openresty, PHP, MySQL, FTP. **Node.js на нём нет** и в
описании тарифов не упоминается; для Node нужна отдельная линейка VDS.

Из этого следует главное для нашего плагина: **сайт должен собираться в
статический экспорт**. В Next.js это `output: "export"` плюс
`trailingSlash: true` — иначе экспорт кладёт `about.html`, и Apache отдаёт его
только по адресу с расширением.

Оптимизацию изображений при экспорте придётся выключить
(`images: { unoptimized: true }`): она требует сервера.

### Одна услуга — не то же самое, что один аккаунт
В личном кабинете может быть несколько услуг хостинга, каждая со своим
логином вида `koo7873294` / `tec7802265`, своим FTP и своим набором доменов.
Отключение одной услуги за неуплату гасит её сайты и не трогает другие.
Прежде чем что-то искать, посмотрите «Управление услугой» — там список.

## 2. Ключевые адреса панели

| раздел | адрес |
|---|---|
| панель услуги | `/hcp2` |
| сайты | `/hcp2/sites/` |
| создание сайта | `/hcp2/sites/create/` |
| карточка сайта | `/hcp2/sites/<домен>/` |
| SSL сайта | `/hcp2/sites/<домен>/security/` |
| установка сертификата | `/hcp2/security/ssl` → «Установить» |
| FTP и SSH | `/hcp2/access/` |
| список услуг | `/hcp2/accounts/` |

Панель требует двухфакторной аутентификации: агент самостоятельно в неё не
входит, работает в уже открытой сессии.

## 3. Создание сайта

«Сайты» → «Создать сайт», три шага:

1. **домен** — предлагается список доменов, привязанных к услуге;
2. **CMS** — вкладка **«Без CMS»**. Там же «Создать базу» (для статики не
   нужна) и **версия PHP: по умолчанию 7.4**. Она снята с поддержки — ставьте
   8.3, если на сайте будет хоть один PHP-обработчик;
3. готово. Корневой каталог получается `/home/<услуга>/<домен>/docs`,
   синоним `www.<домен>` добавляется сам.

## 4. Заливка файлов

FTP: `ftp.<услуга>.nichost.ru`, пользователь `<услуга>_ftp`, корень
`/home/<услуга>`, внутри — каталоги сайтов.

Пароль **не хранится в панели в открытом виде**. «FTP и SSH» → пользователь →
галочка «Выслать пароль на почту» + кнопка **«Сбросить пароль»**: пароль
меняется на новый и показывается во всплывающем окне. Именно показывается —
адрес получателя письма в панели хостинга не виден, он берётся из контактов
кабинета.

Пароль читайте **из разметки страницы, а не глазами со снимка**: в шрифте
панели легко спутать `l` и `I`, `0` и `O`. Одна такая ошибка стоила лишнего
сброса.

Хранить — в диспетчере учётных данных Windows:
```
keyring.set_password('nic-ru-ftp', '<услуга>_ftp', <пароль>)
```

### Механическая выкладка сборки

Порядок больше не пересказывается по памяти, а выполняется скриптом
`scripts/deploy_ftp.py` этого плагина:

```
python deploy_ftp.py --service koo7873294 --domain tech-77.ru --dir out --check
python deploy_ftp.py --service koo7873294 --domain tech-77.ru --dir out --page / --page /contacts/
```

Скрипт берёт пароль из диспетчера учётных данных, заливает каталог сборки в
`/<домен>/docs`, переподключается при обрыве — на нескольких сотнях файлов
сессия общего хостинга рвётся штатно — и в конце сверяет живой сайт со сборкой
по `buildId` из разметки и по метатегу `robots`. «Команда отработала без
ошибки» и «сайт обновился» — разные события, поэтому сверка встроена, а не
оставлена на потом. Ничего на сервере не удаляется: файлы прошлых сборок
остаются лежать, на них никто не ссылается.

**Запускает команду человек в своём терминале, а не агент из своей сессии.**
Измерено 16.09.2026 на SRVLM01: команды агента Claude Code идут через прокси
песочницы, а он пропускает только HTTP и HTTPS. Любое прямое соединение
сокетом падает с `PermissionError [WinError 10013]` — и 21-й порт, и 22-й, и
даже 443-й.

Отличить это от закрытого фаервола можно за один прогон: в ту же секунду
`curl` по 443 отвечает `200`, а `socket.create_connection` на тот же адрес и
порт получает 10013, и в окружении заданы `HTTP_PROXY` и `HTTPS_PROXY`. Если
картина такая — на фаервол машины, VPN и kill switch время не тратить и в их
настройки не лезть: правила машины тут ни при чём.

Рабочая связка: агент собирает сайт и печатает готовую команду, человек
запускает её у себя, вывод сверки возвращается агенту.

## 5. Ловушка `.htaccess`: `%{HTTPS}` за прокси

**Симптом:** сайт залит верно, но отдаёт бесконечный `301` на самого себя и
не открывается вовсе.

**Причина:** TLS завершается на фронтальном openresty, до Apache запрос
доходит обычным HTTP. Переменная mod_rewrite `%{HTTPS}` читается из mod_ssl,
которого на узле нет, и потому **всегда равна off — даже для https-запросов**.
Правило «перевести на https, если не https» срабатывает на каждом запросе.

Измерено пробником на живом сервере:

| запрос | `%{HTTPS}` | `X-Forwarded-Proto` | `$_SERVER['HTTPS']` в PHP |
|---|---|---|---|
| по HTTP | off | `http` | не задан |
| по HTTPS | **off** | `https` | `on` |

PHP видит `HTTPS=on`, потому что значение подставляет тот же прокси, — на это
легко купиться, проверяя php-скриптом. До mod_rewrite оно не доходит.

**Неверно:**
```apache
RewriteCond %{HTTPS} !=on
RewriteRule ^(.*)$ https://example.ru/$1 [R=301,L]
```

**Верно:**
```apache
RewriteCond %{HTTP:X-Forwarded-Proto} !=https
RewriteRule ^(.*)$ https://example.ru/$1 [R=301,L]
```

Пробник для проверки (положить, снять показания, **удалить**):
```php
<?php header('Content-Type: text/plain');
foreach (['HTTPS','HTTP_X_FORWARDED_PROTO','REQUEST_SCHEME','SERVER_SOFTWARE'] as $k)
    echo "$k=" . ($_SERVER[$k] ?? '(нет)') . "\n";
```

## 6. Порядок, который бережёт от аварии

**Сертификат выпускается раньше, чем заливается `.htaccess` с принудительным
HTTPS.** Иначе получается замок: HTTP уводит на HTTPS, а HTTPS не поднимается
из-за отсутствия сертификата, и сайт недоступен ни по одному протоколу.

Если авария уже случилась — переименуйте `.htaccess` в `.htaccess.off` по FTP,
почините, верните обратно.

## 7. Выпуск сертификата Let's Encrypt

**Панель Руцентра сама Let's Encrypt не выпускает.** Она умеет только принять
готовый. Поэтому: выпускаем снаружи, сохраняем файлами, загружаем в панель.

Готовый скрипт: `issue_cert.py` (шаблон в конце раздела). Схема:

1. подтверждение владения **HTTP-01**: файл кладётся по FTP в
   `<сайт>/docs/.well-known/acme-challenge/` и забирается Let's Encrypt по
   HTTP. Работает, потому что до установки `.htaccess` порт 80 отдаёт файлы
   напрямую. DNS трогать не нужно;
2. **сначала испытательный сервер**
   `https://acme-staging-v02.api.letsencrypt.org/directory` — он безлимитный
   и ломается там же, где сломался бы боевой. У боевого лимит пять выпусков
   на домен в неделю, и сжечь его отладкой очень легко;
3. затем боевой `https://acme-v02.api.letsencrypt.org/directory`;
4. на выходе — цепочка PEM (лист + YR2 + корневой ISRG) и приватный ключ.

Проверка перед загрузкой — что ключ действительно от этого сертификата:
```python
key.public_key().public_numbers() == cert.public_key().public_numbers()
```

### Загрузка в панель
`/hcp2/security/ssl` → «Установить». Поля: сертификат, промежуточный, ключ,
пароль ключа. **Файлы прикладываются скрепкой.** Полная цепочка в поле
«Сертификат» принимается, отдельный промежуточный не требуется.

Приватный ключ **не вставляйте текстом через агента**: всё, что печатается в
команде, оседает в журнале сессии. Загрузку файла выполняет человек — во
встроенном браузере агент не может управлять системным диалогом выбора файла.

## 8. Проверка результата

Проверять **со сверкой имени хоста**. Это не формальность: в августе сессия
проверяла `curl -k` и `openssl s_client` без `-verify_hostname`, получила
«сертификат валиден» и закрыла задачу — а у посетителей был
`NET::ERR_CERT_COMMON_NAME_INVALID`, потому что нужного имени не было в SAN.
Ошибку нашли только по скриншоту с телефона.

```python
ctx = ssl.create_default_context()          # проверка имени включена
s = ctx.wrap_socket(socket.create_connection((ip, 443)), server_hostname=host)
[v for k, v in s.getpeercert().get('subjectAltName', ()) if k == 'DNS']
```

Обращайтесь к серверу **по IP с подстановкой имени в Host и SNI**: если у
домена несколько A-записей, обычный запрос может уйти на чужой узел, и
диагностика уедет не туда.

Проверить надо все четыре сочетания: `http://домен`, `https://домен`,
`http://www`, `https://www`.

---

## 9. Чего в этой инструкции нет

DNS. Зоны разных доменов холдинга живут в разных местах: у одних Яндекс, у
других сам Руцентр. Прежде чем менять A-запись, выясните, кто держит зону, и
**не переключайте NS** — на Яндексе к ним привязана почта, и переключение её
ломает.
