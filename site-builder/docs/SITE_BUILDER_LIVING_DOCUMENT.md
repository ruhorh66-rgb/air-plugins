# site-builder — Living Document

Канонический живой документ продукта `site-builder` (DEV-040, «Живая инструкция
продукта»). Описывает фактическую модель продукта **на текущий момент**, не
историю разработки. Путь зафиксирован машинно в `.claude-plugin/plugin.json`
(`living_document`). Второго документа с тем же назначением быть не должно —
`README.md` и `VENDOR.md` остаются справочными (README — краткий обзор для
внешнего читателя, VENDOR — происхождение вендорного кода), они не заменяют
и не дублируют этот файл.

Startup read-order для этого продукта: `.claude-plugin/plugin.json` → этот файл
→ `docs/GOAL.md` (текущий план/цикл) → активная задача в `010_Task_Control_
Platform`, если она заведена. Восстанавливать модель продукта из истории чата
или памяти модели запрещено.

---

## 1. Назначение и capabilities

`site-builder` превращает **бриф** (`brief.yaml` + контент-документы) в
готовый **динамический сайт**: Next.js (App Router) + TypeScript + Tailwind +
shadcn/ui + Framer Motion. Продукт заточен под **редкое, эпизодическое
использование без необходимости помнить рецепт** — вся методика зашита в
скиллы плагина, не в память исполнителя.

Что умеет плагин сегодня:

- прочитать бриф и остановиться с вопросом, если обязательное поле
  отсутствует или неоднозначно (Phase 0 скилла `build-site`);
- подобрать дизайн-направление и дизайн-систему из вендорных баз
  (`design-taste-frontend`, `ui-ux-pro-max`, `design-system`) — не изобретая
  палитру/типографику заново;
- собрать Next.js-проект и вёрстку страниц (`ui-styling` + shadcn/ui +
  Tailwind), с анимацией по гайду `emil-design-eng` и Framer Motion;
- сгенерировать визуалы под сайт через Glif MCP (опционально, см. §5) или
  явно пометить заглушки, если Glif недоступен;
- собрать (`npm run build`) и показать превью локально, прогнать
  `improve-animations` (аудит движения, read-only — план правок применяет
  исполнитель, не сам аудит) и валидатор токенов вёрстки
  (`html-token-validator.py`);
- отдать `SITE_REPORT.md` с составом сборки, выбранным стилем/палитрой,
  списком сгенерированных/заглушечных визуалов и инструкцией по запуску.

Отдельно от основного пайплайна в плагине лежит утилитарный скилл
`issue-ssl-cert` (выпуск Let's Encrypt-сертификата без CLI-клиента и без
регистрации аккаунта) — самостоятельная возможность, не часть цепочки
бриф→сайт, используется при проблемах с HTTPS на уже выпущенном сайте.

**Чего продукт не делает по определению (non-goals из `build-site` SKILL.md):**
не публикует и не деплоит без явного решения пользователя; не придумывает
бренд/юридический/маркетинговый контент — берёт из брифа и спрашивает, если
не хватает; не изобретает дизайн-базу поверх вендорной; не является
пайплайном для серийной генерации сайтов — один бриф = один сайт за прогон.

## 2. Операционная модель

Работа запускается **по решению человека**, разово, на один бриф:
командой `/site <папка-брифа>` (см. `commands/site.md`) либо прямым
делегированием агенту `site-builder` (изолированный контекст, чтобы вёрстка
страниц не раздувала контекст основной сессии).

Cadence — по требованию (on-demand), регулярного/периодического запуска нет
и не предполагается. Фазы одного прогона (Phase 0–5 скилла `build-site`):
чтение брифа → дизайн-система и направление → скаффолд Next.js → сборка
страниц/компонентов и визуалов → верификация сборки/превью и аудит анимации
→ хэндофф с `SITE_REPORT.md`.

Самообучение продукта — не БД/стор, а дописывание находок в
`skills/build-site/references/stack.md` и в сам `SKILL.md` после реальной
сборки (Core §2.5 self-documentation). Отдельного SQLite-стора обучения
(паттерн, обязательный по решению ЛПР 13.08.2026 для остальных продуктов
контура) на момент этой записи в плагине **нет** — это известный хвост, а
не немедленный дефект (см. §7 «Known degraded modes»).

## 3. Human gates

- **Публикация/деплой сайта — только решением ЛПР.** Ни скилл, ни агент не
  деплоят и не публикуют самостоятельно ни при каких обстоятельствах
  (`build-site/SKILL.md` Non-goals; `agents/site-builder.md` Rules).
- **STOP-ASK на пробелах брифа.** Обязательное или неоднозначное поле
  (назначение, аудитория, страницы, язык) — повод остановиться и спросить,
  не угадывать (Phase 0).
- **Бренд-критичные визуалы не генерируются.** Логотип и юридически/
  маркетингово значимые изображения — только от пользователя, не черновик
  от Glif (Phase 3b).
- **Новый цикл `docs/GOAL.md` — только через Confirm ЛПР** по каждому
  пункту (DEV-060, «Один адрес плана»); оформление плана не есть его
  исполнение. На момент этой записи следующий цикл (0.3.0) числится
  `draft_for_review` и работа по нему не начата.
- **`review-animations` вызывается только пользователем** — апстрим пометил
  его `disable-model-invocation: true`, модель не может вызвать его сама
  (Phase 4, `agents/site-builder.md`).

## 4. Integrations / providers

- **Glif MCP** (`.mcp.json`, `https://glif.app/api/mcp`) — генерация
  визуалов (hero, иллюстрации, иконки, OG-изображения). **Опционален**:
  требует `glif_api_token` (userConfig, sensitive, `required: false`). Без
  токена продукт не блокируется — переходит на явные помеченные заглушки
  (см. §7).
- **`impeccable`** (внешний, не вендорится) — необязательный аудит качества
  дизайна; используется в Phase 4, только если пользователь сам установил
  (`npx impeccable install`). Плагин не ставит и не требует его.
- Node.js на PATH — обязательная локальная зависимость сборки (без внешнего
  сервиса).

## 5. Source-of-truth boundaries

Вендорные скиллы дизайна и их базы данных — **read-only с точки зрения
продукта**, правятся только через переоформление вендоринга (обновление
`VENDOR.md` с новым upstream-коммитом), не патчатся точечно:

| Скилл(ы) | Источник | Лицензия | Зафиксированная версия/коммит |
|---|---|---|---|
| `ui-ux-pro-max`, `design-system`, `ui-styling`, `design`, `brand`, `slides`, `banner-design` | `nextlevelbuilder/ui-ux-pro-max-skill` | MIT | v2.11.0, `f8ac5e1…` (2026-07-19) |
| `design-taste-frontend` | `Leonxlnx/taste-skill` | MIT | `98565e6…` (2026-07-20) |
| `emil-design-eng`, `review-animations`, `improve-animations` | `emilkowalski/skills` | MIT | `6bf2443…` (2026-07-20) |

Обоснование вендоринга (не runtime-install): предсказуемая работа спустя
месяцы без сети/установщика — продукт эпизодического использования
(`VENDOR.md`). `issue-ssl-cert` и оркестрирующий скилл `build-site` —
собственный код плагина, не вендорный; их можно и нужно править напрямую.

## 6. Current release baseline

- Версия: **0.2.2** (`.claude-plugin/plugin.json`, поле `version`).
- Второго манифеста `.codex-plugin` у продукта на сегодня нет — сверка
  версий между манифестами (DEV-060, шаг 4 выпуска релиза) для этого
  продукта пока неприменима, проверять нечего.
- `defaultEnabled: false` — плагин ставится выключенным, потому что
  подключается к внешнему сервису (glif.app); включение — осознанное
  действие пользователя.
- Установка — из локального маркетплейса `E:/-7-` (`air-plugins`); правка
  файлов в `E:\-7-` сама по себе не влияет на запущенный плагин, он
  работает из кэш-копии `~/.claude/plugins/cache/air-plugins/` до апдейта
  версии и `claude plugin update`.

## 7. Known degraded modes

- **Нет `glif_api_token`** → генерация визуалов пропускается, вместо неё —
  явные помеченные заглушки, перечисленные в `SITE_REPORT.md`; сборка не
  блокируется (Precondition 2, Phase 3b).
- **Гейты качества сегодня — частично текст, не измерение.** По
  самооценке в `docs/GOAL.md` §1.2 (план 0.3.0, `draft_for_review`, ещё не
  подтверждён ЛПР): реально измеряется скриптом сегодня — сборка
  (`npm run build`), рендер в превью и валидатор токенов вёрстки
  (`html-token-validator.py`). Доступность, контраст, LCP/CLS, битые
  ссылки, JSON-LD/schema.org — перечислены в `SKILL.md` как требования, но
  **не проверяются автоматически ни одним скриптом** на дату записи;
  соответствие этим пунктам сегодня — утверждение модели, не гейт. Если
  план 0.3.0 будет подтверждён ЛПР и выполнен, эта строка обязана быть
  переписана в рамках write-back contract (§9).
- **`impeccable`** — необязательный аудит, включается только при ручной
  установке пользователем; при отсутствии установки Phase 4 проходит без
  него, и это штатный (не деградированный) режим, а не пробел.
- **Стор обучения (SQLite) отсутствует** — контурное правило 13.08.2026
  требует его для каждого плагина; у `site-builder` его на сегодня нет.
  Признаётся как известный хвост, не как то, что скрывается.

## 8. Канонические entrypoints

- Скилл: **`skills/build-site`** (`SKILL.md`) — единственная точка входа в
  логику сборки сайта, фазы 0–5.
- Агент: **`agents/site-builder`** (`agents/site-builder.md`) — изолированный
  контекст, следует скиллу `build-site` дословно (фазы 0–5), не пересказывает
  и не переопределяет его.
- Команда: **`/site <brief-folder>`** (`commands/site.md`) — тонкий
  загрузчик, вызывает `build-site`; согласно DEV-040 не является вторым
  конкурирующим источником инструкции.
- Утилитарный скилл вне основного пайплайна: **`skills/issue-ssl-cert`**.

## 9. Write-back contract

Любое изменение capabilities, бизнес-логики, human gates, интеграций,
runtime-entrypoints, release-state или source-of-truth boundary продукта
обязано в том же цикле обновить этот документ. Изменение без обновления
этого файла считается незавершённым (DEV-040, Write-back contract).

## 10. Текущие состояния (четыре блока DEV-040)

- **Текущие бизнес-обязательства.** Не зафиксированы в этом репозитории —
  продукт не ведёт собственного бизнес-плана/cadence в `docs/`; если такие
  обязательства существуют, их источник — реестр `010_Task_Control_
  Platform`, за пределами этого прогона не проверялся (см. «Что не удалось
  заполнить» в отчёте исполнителя).
- **Текущие обязательства по разработке.** Единственный актуальный план —
  `docs/GOAL.md` («site-builder 0.3.0 — измеримые гейты и делегирование»),
  статус `draft_for_review`: измеримые гейты на скриптах, делегирование
  субагентам с назначенной моделью; работа не начата до Confirm ЛПР.
- **Открытые human gates / блокеры.** Confirm ЛПР по плану 0.3.0 (в частности
  развилка §6 плана: правки кода плагина исполнитель делает сам или через
  рой); публикация/деплой любого собранного сайта — отдельное решение ЛПР
  каждый раз.
- **Следующие автономные действия.** Без нового Confirm ЛПР — ни одного:
  план 0.3.0 не начат, автоматизации/контроллеров/воркеров нет (см. §2), а
  цикл продукта запускается только по прямому обращению пользователя с
  брифом.
