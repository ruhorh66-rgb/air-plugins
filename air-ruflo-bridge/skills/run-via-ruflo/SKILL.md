# Run via Ruflo

## Читай это первым, если собираешься править сам скилл

Всё, что написано ниже, месяц не действовало. Правки заезжали в источник, версия в
манифесте росла, а сессии продолжали читать текст от 30.07: плагин оставался
УСТАНОВЛЕННЫМ на 0.4.1 при манифесте 0.6.1. Именно поэтому «с роем каждый раз одни и
те же проблемы» — исправления порядка запуска и критерия приёмки не доставлялись
физически. Разбор: `ERR-2026-000203`.

Доставка требует ТРЁХ шагов, а не двух:

```
1. поднять version в .claude-plugin/plugin.json
2. пересобрать копию в кэше маркетплейса
3. claude plugin update air-ruflo-bridge@air-plugins
```

Третий обязателен. Бамп сам по себе только создаёт каталог в кэше и НЕ
переустанавливает плагин, а `claude plugin update` при равных версиях отвечает
успехом — расхождение не сигналит ничем. Проверка одна: в выводе должна быть строка
`updated from X to Y`. Ответ «уже последняя версия» на только что внесённую правку —
признак дефекта, а не подтверждение.

Расхождение теперь видно на старте сессии: хук `plugin_delivery_check.py`
(Модуль 5 § 10.4) печатает состав плагинов и называет сторону — «отстала установка»
лечится обновлением, «не запушено» лечится только push.

Use the real Ruflo CLI; do not implement a swarm or orchestration substitute.

Before any engine upgrade or new run profile, read `docs/RUFLO_COMPONENT_AUDIT_2026-09-07.md`. The 2026-08-14 assumption that `ruflo-core` is only an MCP donor is superseded. Current upstream separates plugin-lite from the full CLI loop; AIR validates full-loop capabilities first and treats sibling plugins as task-triggered additions unless the audit/profile marks them required.

## Где искать ответ про сам движок — порядок обязательный

Указание ЛПР 10.08.2026: «поменьше лезь в исходники, побольше в репозиторий и help;
эта информация есть на гитхабе, а мы раз за разом лезем в исходники». Замечание по
делу — за один вечер исходник читался четырежды там, где хватило бы одной команды.

**Порядок:**

1. `ruflo <команда> --help` и `ruflo <команда> <подкоманда>` — у движка развитая
   штатная справка, и она отвечает на большинство вопросов НЕМЕДЛЕННО. Примеры,
   проверенные 10.08.2026:
   - `ruflo config providers` — таблица провайдеров с приоритетом и статусом;
   - `ruflo doctor` — диагностика; `ruflo status` — состояние;
   - `ruflo <команда> --help` — подкоманды и флаги.
2. Официальные документы: репозиторий `github.com/ruvnet/claude-flow`,
   `docs/USERGUIDE.md`. Это первоисточник, и он же — правило контура
   `prefer-official-sources`.
3. **Исходники — только когда доки расходятся с наблюдаемым.** Тогда чтение кода
   обязательно и оно закрывает вопрос: так был найден лимит `validateText` в 10 000
   знаков (`ERR-2026-000214`), которого нет ни в справке, ни в доках.

**Копию апстрим-документации здесь НЕ заводим.** Второй источник на один смысл
расходится через неделю, и никто не знает, какой правдивый, — то же правило, по
которому `ROADMAP.md` свёрнут в `docs/GOAL.md`. В этом файле держится только ДЕЛЬТА:
что у нас настроено иначе и где наблюдаемое разошлось с документацией.

### Провайдеры моделей — у движка свой слой, наш роутер ему не нужен

Проверено штатной командой 10.08.2026 (`ruflo config providers`):

| провайдер | модель по умолчанию | приоритет | статус |
|---|---|---|---|
| anthropic | claude-3-5-sonnet-2024… | 1 | **Active** |
| openrouter | claude-3.5-sonnet | 2 | Disabled |
| ollama | llama3.2 | 3 | Disabled |
| gemini | gemini-2.0-flash | 4 | Disabled |

Управление — `--add`, `--remove`, `--enable`, `--disable`. Модель на агента задаётся

Отсюда решение прошлых сессий, которое здесь и фиксируется: **свой HTTP-роутер
(`E:\-4-\codex-shim\air_llm_router.py`) для роя не нужен** — движок маршрутизирует
сам, с приоритетами и failover. Роутер остаётся как отдельный инструмент контура, но
в схему запуска роя не входит.

### Удешевление прогона — команды движка, а не наши выдумки

Проверено штатной справкой и живым вызовом 11.08.2026. Механизм у движка есть,
но он **не перехватывает сам** — его надо спросить.

```
ruflo hooks model-route   -t "<задача>"                  # haiku/sonnet/opus по сложности
ruflo hooks model-route   -t "…" --prefer-cost
ruflo hooks model-outcome -t "…" -m sonnet -o success    # ЗАПИСЬ ИСХОДА — без неё не учится
ruflo hooks model-stats   [--detailed]                   # что накоплено роутером моделей
ruflo hooks explain       -t "<задача>"                  # про выбор АГЕНТА, не модели
ruflo hooks token-optimize --stats                       # Agent Booster
```

**Две команды, а не одна.** `model-route` спрашивает совет, `model-outcome`
записывает исход — приоры обновляет ВТОРАЯ. Вызовы одного лишь `model-route` не
учат роутер ничему; первая редакция этого раздела утверждала обратное и была
неверна (codex review 11.08.2026).

**`hooks_route` и `hooks_model-route` — разные инструменты.** Первый маршрутизирует
ТИП АГЕНТА (coder/tester/reviewer) и модели не возвращает вовсе; второй — модель.
Я перепутал их в первой редакции шаблона цели, то есть вписал в боевой запуск вызов,
который не мог дать того, ради чего вписан. `hooks explain` объясняет решение
ПЕРВОГО и без `-t` просто падает.

Как отвечает на самом деле (наш прогон, не документация):

| задача | вердикт | уверенность | заявленная экономия |
|---|---|---|---|
| «исправить опечатку в комментарии» | SONNET | 51 % | 80 % против opus |
| «спроектировать единый источник правды…» | OPUS | 57 % | — |

Реализация — `heuristic-thompson-bandit`, тот самый самообучающийся роутер из
`docs/USERGUIDE.md`. Он живой, но **на малой статистике врёт**: сложную задачу выше
он оценил как «low, 21 %» и всё равно выдал Opus. Корректируется примерно после 50
исходов, а исходы копятся ТОЛЬКО от вызовов.

**Замер 08–11.08.2026, девять боевых прогонов:** `hooks_route` вызван **ноль раз**;
сигналов `[TASK_MODEL_RECOMMENDATION]` и `[AGENT_BOOSTER_AVAILABLE]` в логах **нет
вовсе**. Отсюда и наши 88 % ответов на Opus — не потому что механизм плох, а потому
что его не звали. С 11.08 требование звать его вписано в шаблон цели `run_task.ps1`.

### ФОРМА ПОСТАНОВКИ — четыре части, иначе гейт целеполагания не пройден

Записано 12.08.2026 после того, как ЛПР забраковал постановку `air-storage 0.3.0`
целиком. Три дефекта в одном тексте, все три — типовые.

**1. Цель — это СОСТОЯНИЕ, а не работы и не мотив.** Таблица фактов «что станет
истинным», у каждого — способ проверки, и замер «истинных фактов N из M» на сегодня.
Форма уже принята в контуре: `010/02_WIKI/AIR-STORAGE — цель как состояние и схема
реализации`. Раздел «зачем этот релиз» целью **не является**: он объясняет мотив и не
даёт критерия готовности. Дословно: «ты пишешь мне, зачем этот релиз? Это не цель».

**2. Метрики — ПРОДУКТА, а не расхода прогона.** Числа, к которым продукт обязан
прийти: было → порог. Доллары, ходы и доля Opus — метрика исполнителя, она не заменяет
метрику проекта. Смысл: **рой проверяет себя сам**, не дожидаясь человека, а «сделано»
без сдвига метрики не считается сделанным.

**3. Технические развилки решает исполнитель.** «Считать ли md5 рядом с sha256», «какой
каталог назначения» — не выносятся ЛПР. ЛПР решает **приоритет и границы**; способ —
забота исполнителя, и принятое решение записывается в постановку вместе с метрикой, по
которой видно, сработало оно или нет.

**4. Приоритет ставит ЛПР, и он не совпадает с «что проще».** В том же разборе перенос
инструментария волтов сессия пометила «не срочным», а ЛПР назвал основным: «без
graphify, без замены Dataview, без создания волтов — чем занимается механизм? просто
тупые прогоны по диску». Признак ошибки приоритета: работа устраняет известные дефекты,
но не добавляет способности.

**Связь с экономикой** (указание ЛПР 12.08): «чем лучше проработаем задачу, тем меньше
прогонов». Плохо поставленная задача возвращается прогонами, а не правками текста.

### НАСТРОЙКИ ПРОГОНА — ФАЙЛОМ, ВЕРСИЮ ПЛАГИНА НЕ ПОДНИМАТЬ

Замечание ЛПР 12.08.2026: «настройки — это штатная операция», и оно справедливо. До
этого умолчания лежали в коде скрипта, и смена модели Queen потребовала бампа версии,
тега и доставки — то есть **выпуска ради настройки**.

```
E:\-4-\ruflo-hive\run-config.json    queen_model · workers · prefer_cost · autopilot
E:\-4-\ruflo-hive\engine.json        версия движка и откат
```

**Правка этих файлов версии не требует.** Ни бампа, ни тега, ни `plugin update`.

Старшинство: явный параметр вызова → файл настроек → встроенное умолчание. Файла нет —
работаем на встроенных, и это **называется в отчёте**, а не подразумевается.

Версия поднимается только когда меняется МЕХАНИЗМ: как настройка применяется, что
проверяется, какой контракт у отказа. Значение настройки механизмом не является.

### МОЛЧАЩИЙ ЖУРНАЛ КООРДИНАТОРА — НЕ ПРИЗНАК ОБРЫВА

Записано 12.08.2026 по своей же ошибке: журнал Queen не пополнялся 12 минут,
процессорное время не росло — прогон был объявлен оборвавшимся и доложен ЛПР как
«оборвалась». В те же минуты рой писал файлы: проектный документ точки входа, план
плагина, правки двух модулей. Работали субагенты, у них свои журналы; координатор
молчал, потому что **ждал их возврата**.

**Прежде чем объявить обрыв — смотреть ПРОДУКТ РАБОТЫ**, а не журнал координатора:
файлы в целевом каталоге, коммиты, артефакты.

Поодиночке ничего не значат: журнал не пополняется, процессорное время не растёт,
дочернего Claude не видно в списке, записи `result` нет. Признак обрыва — **отсутствие
продукта за окно И мёртвый держатель замка**, оба условия сразу.

Цена ошибки несимметрична: подождать лишние десять минут дёшево, оборвать живой
прогон — дорого. Ложное «оборвалось» толкает снять замок и перезапустить, то есть
убить работающее.

### ПРИЁМКА ОТВЕЧАЕТ «РОЙ РАБОТАЛ», НО НЕ «РОЙ ПОЛУЧИЛ ЗАДАНИЕ»

Проверка вызовов `mcp__claude-flow__` говорит, что рой шевелился. Она **не** говорит,
что он получил постановку, — и 12.08.2026 это стоило прогона: `TASK-OBS-0052` закрылся
как `success`, сделав треть, потому что до роя доехали две строки из 6477 знаков.

Поэтому после прогона сверять, что постановка доехала: искать в сохранённом движком
промпте (`.hive-mind\sessions\hive-mind-prompt-*.txt`) путь к файлу постановки и
ключевые разделы делегирования. Их отсутствие — несостоявшийся прогон, независимо от
кода возврата и от того, получен ли какой-то предметный результат.

Класс шире случая: это общий вид дефекта «исполнитель работал, но не над тем». Тот же
вопрос задавать любому исполнителю — субагенту, Codex, локальной модели.

### ПОСТАНОВКА ПЕРЕДАЁТСЯ ФАЙЛОМ — движок обрезает текст цели

Установлено замером 12.08.2026 и воспроизведено на синтетической цели.

**Что происходит.** Движок обрезает объектив при сборке промпта. В сохранённом им же
файле `.hive-mind\sessions\hive-mind-prompt-*.txt` от постановки в 6477 знаков остаются
**две строки**; обрыв приходится на первую запятую или тире внутри строки `title:`.
До Node аргумент доезжает целиком — проверено печатью `process.argv`, — то есть режет
сам движок, а не наша передача.

**Чем это стоило.** Прогон `TASK-OBS-0052` сделал треть работы и был закрыт как
`success`: Queen честно сообщила «текста задачи на диске нет» — она его и не получала,
а где лежит файл, ей никто не сказал. Приёмка этого не заметила: вызовы
`mcp__claude-flow__` были, секретов нет, движок вернул 0. **Проверка «рой работал» не
отвечает на вопрос «рой знал, что делать».**

**Как чинится.** В цель кладётся ПУТЬ к файлу постановки, а не её текст; сессия читает
файл первым действием. Так снимается и ограничение на длину: постановка может быть
любой. `run_task.ps1` делает это сам — цель, поданную даже текстом (`-Objective`), он
кладёт файлом рядом с отчётом, чтобы способ получения был один.

Путь идёт ПЕРВЫМ, до наставлений о работе: обрыв приходится на начало строки, и если
что-то уцелеет, это должно быть указание, где лежит задача.

**Файл всегда КОПИРУЕТСЯ в корень роя — даже когда постановку подали готовым файлом.**
`-ObjectiveFile` теперь указывает, ОТКУДА взять текст, а не что подсунуть сессии: копия
ложится рядом с отчётом, и рой читает её. Причина — отказ `TASK-OBS-0053` 12.08.2026:
Queen получила приказ прочитать и **исполнять** файл из чужого дерева (`E:\-5-\...`) при
работе в третьем (`E:\-8-\...`), назвала это «классическим паттерном, который стоит
подтвердить, а не выполнять вслепую», и задачу не взяла. Вывод сессии верный — чинится
не уговорами, а тем, что постановка лежит в её собственном рабочем каталоге.

По той же причине в цель дописывается, что **гейт уже пройден**: сессия не видит, чем её
запустили, а по описанию моста знает, что прогон без человеческого подтверждения —
подозрительный. Тот отказ прямо назвал это второй причиной.

### ЧЕМ ИСПОЛНЯЕТСЯ АГЕНТ — три пути, и работает у нас один

Установлено 11.08.2026 прямым опросом MCP-сервера движка (не чтением исходников и не
прогоном за деньги: зонд по stdio стоит ноль). Движок отвечает это сам, полем `note`
в ответе `agent_spawn`:

> Agent registered for coordination. Three execution paths: (1) call
> `agent_execute(agentId, prompt)` — direct LLM call via Anthropic Messages API
> (**requires `ANTHROPIC_API_KEY`**); (2) Claude Code Task tool — spawns a real
> subagent; (3) `claude -p` — headless background instance.

**`agent_spawn` не исполняет ничего.** Он РЕГИСТРИРУЕТ агента: `status: registered`.
Поля `model` и `provider` — запись в базе роя, а не выбор исполнителя. Схема
`agent_spawn` вообще не имеет поля `provider` (проверено: `agentType, agentId,
swarmId, config, domain, model, task, memoryBase, memoryDimension`), а переданный
`provider` молча игнорируется, и модель при этом ещё и переписывается роутером
(`modelRoutedBy: "router"`).

**Путь (1) у нас мёртв и оживить его нечем.** Он ходит в Anthropic Messages API по
`ANTHROPIC_API_KEY`, а у контура API-ключа нет — есть подписка Claude Code, которая
через API не работает. Замер: `agent_execute` возвращает `success: false, model:
claude-sonnet-5, error: "fetch failed"` за **3–14 миллисекунд** — это не сеть, это
некому звонить. Так же он падал и в боевом прогоне 0043.

**OpenRouter здесь не помогает.** `providers configure -p openrouter` проходит и
пишет ключ (11.08.2026 сделано, ключ лежал в `E:\-4-\codex-shim\openrouter.key`), но
в таблице провайдер встаёт как `Custom / (not specified)`, `providers test` отвечает
`No test endpoint available`, а `agent_execute` всё равно идёт в Anthropic API. То
есть настройка провайдера — не рычаг: путь (1) в этой версии умеет только Anthropic.

**Работает путь (2): Task-субагент Claude Code.** Он исполняется нашей подпиской, и
модель у него задаётся — определением субагента (`model:` во frontmatter) либо
параметром вызова. Значит удешевление достигается ЗДЕСЬ, а не настройкой провайдеров:
Queen должна раздавать работу Task-субагентами с советованной моделью, а не
`agent_execute`. Путь (3), `claude -p --model …`, — то же самое для фоновой
механической работы.

**Отсюда правило постановки.** В цели требовать не «спавни агента с моделью», а
«раздай работу Task-субагентами, модель каждому — по совету `hooks_model-route`».
Формулировка «спавни с посоветованной моделью» исполняется буквально и не даёт
эффекта: спавн — это учёт, а не исполнение.

### Codex — ВОРКЕР роя, а не контролёр

Поправлено 11.08.2026 по указанию ЛПР. В контуре Codex закрепился как «вторая пара
глаз» на приёмке, и это сужение: его собственное описание говорит прямо — забирать у
Claude Code **существенную работу по коду**, а не только проверять сделанное
(`agents/codex-rescue.md`: «hand a substantial coding task to Codex»).

Он и устроен как воркер: субагент — тонкая обёртка, делающая ОДИН вызов `Bash` к
runtime-скрипту. Значит рою он доступен **напрямую, без инструмента `Task`**:

```
node <плагин codex>/scripts/codex-companion.mjs task --background --write "<кусок работы>"
node <плагин codex>/scripts/codex-companion.mjs status <job-id>
node <плагин codex>/scripts/codex-companion.mjs result <job-id>
```

`--write` — Codex правит файлы сам (это и делает его воркером, а не советчиком);
`--background` + `status`/`result` — асинхронная выдача, ровно то, что нужно рою:
раздал кусок, пошёл дальше, забрал результат.

**Почему это важнее, чем кажется.** Отказ классификатора в прогоне 0043 был на
инструменте `Task` с `subagent_type: codex:codex-rescue`. Прямой вызов runtime через
`Bash` этого замка не касается — то есть Codex как воркер доступен рою **уже
сейчас**, без правки `autoMode.allow` человеком. Путь через `Task` остаётся вторым и
требует ключа (см. раздел про классификатор).

Одна ловушка пути: `${CLAUDE_PLUGIN_ROOT}` вне контекста самого плагина не определён,
а абсолютный путь содержит версию (`…\codex\1.0.6\…`) и ломается на её бампе. Значит
в цель подаётся шим, а не литерал версии, — тем же образом, что `E:\-4-\bin\codex.cmd`
заведён для самого Codex CLI.

**Первый уровень маршрутизации (Agent Booster, $0) у нас ОТСУТСТВУЕТ.**
`token-optimize --stats` говорит прямо: `agentic-flow not available (using
fallbacks)`, `Agentic-Flow Active ✗`, сэкономлено 0 токенов, попаданий в кэш 0 %.
То есть самый дешёвый уровень из трёх просто не установлен. Ставить его — отдельное
решение, не побочный эффект чужой задачи.

### МЕТРИКИ ПОСТАНОВКИ — ВТОРАЯ ПРИЁМКА, И ОНА МАШИННАЯ

Указание ЛПР 13.08.2026 после прогона `TASK-OBS-0053`. Тот прогон закрылся как `done`:
рой работал (39 вызовов), выпустил 1.4.0, тесты 115 из 115 зелёные — и **ни один из
десяти порогов постановки не сдвинулся**. Живых действий рой не делал, они необратимые,
и это правильное решение; неправильно то, что приёмка не заметила и очередь пометила
задачу готовой, а следом выдала кнопку на следующую.

Метрики заводились ради двух вещей сразу: чтобы человек видел движение и чтобы **рой сам
понимал, что ещё не сделано**. Пока их никто не читает машинно, они украшение.

Поэтому рой обязан положить рядом с отчётом `metrics-<TaskId>.json`:

```json
{"task":"TASK-OBS-0053","metrics":[
  {"name":"строк в closure_receipts","before":"0","threshold":">=2","after":"0",
   "reached":false,"how":"select count(*) из comms.sqlite3"}]}
```

Три исхода, тот же контракт, что у скана секретов: **все пороги достигнуты** → прогон
закрывает задачу; **часть не достигнута** → выход 12, названо сколько и какие;
**файла нет** → выход 12 и «ПРЕДЪЯВИТЬ НЕ СМОГ», что не то же самое, что «метрик не
требовалось».

`reached: false` с названной причиной — нормальный исход. Приписанный — подлог,
вскрывается первой же проверкой человеком.

## One swarm for the whole contour — не обсуждается

Состояние ruflo привязано к РАБОЧЕМУ КАТАЛОГУ: команда, поданная из другого cwd,
заводит там свой `.hive-mind` и `.claude-flow` и считает себя отдельным роем. Так
на 05.08.2026 в контуре оказалось **девять каталогов состояния при нуле живых
процессов**, три из них рапортовали `running: true`.

Канонический корень — `E:\-4-\ruflo-hive`. Он стоит умолчанием в `run_task.ps1` и
`install_ruflo.ps1`; передавать `-ProjectRoot` не нужно. Другой корень скрипт
**отвергает с кодом 5**, а не берёт молча: тихое согласие вернуло бы ту же россыпь.

Отсюда следует то, ради чего всё и делалось: **рой накапливает опыт в одном месте**,
а не начинает с нуля в каждом каталоге.

Две вещи, которые раньше путались и теперь разведены:

| | |
|---|---|
| `-ProjectRoot` | где живёт СОСТОЯНИЕ роя — всегда канонический корень |
| `-WorkDir` | где выполняется КОМАНДА — каталог проекта, по умолчанию текущий |

Перед прогоном `run_task.ps1` сам берёт замок и снимает его в `finally`, в том числе
после падения. Занятый замок живой сессии — команда **присоединиться**, а не поднять
второй демон: выход 4 означает «рой уже работает», а не «ошибка».

### Протокол владения замком

Занятость роя знает ОДИН источник — замок `hive.lock.json` в корне, общем с очередью.
Строка очереди — производная запись: она говорит, что задача взята в работу и кем, но
на вопрос «свободен ли рой прямо сейчас» не отвечает и ответить не может.

Право действовать даёт **владение**, а не наблюдение. Поэтому `claim` создаёт замок
одной операцией ядра (`CreateNew`, он же `O_EXCL`), а протухший замок **перехватывает
на месте** под эксклюзивной ручкой (`FileShare::None`) — не удаляя файл. Удаление
адресует файл по имени, а решение принимается по содержимому, прочитанному раньше;
между этими моментами имя успевает указывать на другой файл, и два претендента
получают один рой. Файл не удаляется — подменять нечего.

| случай | исход |
|---|---|
| замок битый или нечитаем | `unknown`, выход 5 — это НЕ «свободно» и НЕ «занято», разбирает человек |
| PID переиспользован | держатель опознаётся парой PID + время старта процесса; чужой процесс с тем же номером даёт `stale`, и замок перехватывается |
| падение между замком и записью строки | строка чинится ПО ЗАМКУ (`reconcile` при следующем взятии): в замке лежит `taskId`, значит строку можно восстановить, а не гадать |
| падение после записи строки, замок остался | замок мёртвого держателя — мусор, а не занятость: следующий `claim` его перехватывает и снимает пережившие отметки чужих строк |

Вызывающий на Python регистрирует держателем СВОЙ процесс (`-HolderPid`): powershell
завершается сразу после `claim`, и без этого замок протухал бы в момент рождения.

Выдача задачи (`ruflo_queue.py push`) идёт под тем же владением: замок берётся до
всякой правки таблицы, строка переводится `queued` → `offered` и только потом
создаётся кнопка. `offered` значит «заявка уже выдана, ждёт человека» — второй кнопки
на ту же задачу быть не может. Отклонение, просрочка и любой отказ до кнопки резерв
снимают; замок при этом не держится через раздумье человека — пока кнопка висит, рой
ничем не занят.

```
scripts\hive_single.ps1 -Action status        # где рой, жив ли, кто держит
scripts\hive_single.ps1 -Action sweep         # каталоги вне канона (только показ)
scripts\hive_single.ps1 -Action sweep -Fix    # ПЕРЕНОС их в archive, не удаление
```

**Перед любой уборкой** — `python scripts\consolidate_hives.py`. В каталогах роёв
лежат их ОБЪЕКТИВЫ, то есть постановки задач, которых больше нигде нет; сборщик
кладёт их в `E:\-4-\ruflo-hive\hives.sqlite` вместе с сырьём, по ключу SHA-256,
и повторный прогон ничего не задваивает. Удалять до слияния нельзя.

Каталоги ЧУЖИХ живых сессий уборка не трогает без явного `-IncludeForeign`: снять
историю роя у работающей рядом сессии — сломать ей работу, а не навести порядок.

## Проверка на утечку секретов — после каждого исполнения

Рой пишет файлы автономно, и никто не смотрит, не утащил ли он токен в рабочее
дерево. Инцидент этого класса в контуре уже был — ACL-экспозиция `openrouter.key`
на SRVLM01, 01.08.2026.

`run_task.ps1` прогоняет `scan_secrets.ps1` по `-WorkDir` в блоке `finally` —
**всегда**, в том числе после падения: упавший прогон успевает наследить не меньше
удачного. Результат дописывается в отчёт и НЕ подменяет исход самого прогона.

Сканер — `gitleaks` (8.30.1, установлен через winget), а не собственные регулярки:
свой набор шаблонов означал бы, что мы гарантируем то, чего не проверяли.

**Три исхода, ровно как требует `AIR_CONTROL.md`:**

| исход | код | что значит |
|---|---|---|
| `clean` | 0 | проверено, находок нет — рядом чем и за сколько |
| `leaks` | 1 | найдено — рядом файл, строка, правило |
| `unverifiable` | 3 | **ПРОВЕРИТЬ НЕ СМОГ** — рядом почему |

`unverifiable` — это **не «чисто»**. Нет сканера, отказ запуска, таймаут — всё это
даёт третий исход. Молчаливое превращение непроверенного в чистое и есть тот
дефект, ради которого модуль контроля вводили.

**Значение секрета не печатается никогда.** `--redact` включён жёстко: находка
называется местом и правилом, но не содержимым — в отчёте, в логе, в выводе.

Отдельно: `heycupola/relic` (IDEA-000071) для этой проверки **не годится** — это
zero-knowledge ХРАНИЛИЩЕ секретов, а не сканер. Он закрывает другую половину
задачи: если секрет лежит в нём, а не в `.env` рядом с кодом, рою нечего утаскивать.
Профилактика и контроль дополняют друг друга, подменять одно другим нельзя.

## Canonical command, not our own orchestration

Переписано 05.08.2026 по решению ЛПР: контур не собирает `swarm_init`/`task_create` вручную —

### ИСПРАВЛЕНО 08.08.2026 — запуск состоит из ЧЕТЫРЁХ шагов, не одного

Прежняя редакция этого раздела утверждала, что `hive-mind spawn --claude -o "<цель>"`
«сама решает состав роя из цели». **Это неверно, и цена ошибки — все прогоны контура
с 05.08 по 08.08.2026** (`ERR-2026-000192`). Проверено по справке самого движка и по
официальному USERGUIDE:

```text
-n, --count   Number of workers to spawn   [default: 1]      <- состав задаём МЫ
task          Submit tasks to the hive                        <- шаг, который не вызывался
autopilot     Persistent swarm completion — keeps agents
              working until ALL tasks are done                <- шаг, который не вызывался
```

Состояние роя на момент находки: **18 воркеров, все `idle`, `Completed = 0` у каждого**,
Queen `Load 0.0%` с двумя задачами в очереди. То есть рой не выполнил ни одной задачи
ни разу — всю работу делала одна Claude Code сессия, поднятая четвёртым шагом, а
воркерам её никто не раздавал: их был один (дефолт движка), и очередь роя была пуста.

**Правильный порядок, зашит в `run_task.ps1`:**

| # | Команда | Зачем |
|---|---|---|
| 1 | `hive-mind spawn -n <N>` | завести N воркеров (параметр `-Workers`, дефолт 5 — из примера движка) |
| 2 | `hive-mind task -d "<цель>" -p <prio>` | положить задачу **в очередь роя** |
| 3 | `autopilot enable` | держать агентов, пока не закрыты ВСЕ задачи (отключается `-NoAutopilot`) |
| 4 | `hive-mind spawn --claude -o "<цель>"` | Queen-сессия, раздаёт работу воркерам через MCP |

### РАБОЧИЙ РЕЦЕПТ — проверен пробой 08.08.2026, цифры ниже настоящие

Рой умеет многоагентность. Всё, что нужно — **прямо потребовать распределения**;
без этого Queen делает работу сама, и внешне это неотличимо от роя.

Две правки закрыли класс, и обе стоят в машине, а не в тексте:

1. **Требование делегировать дописывается ОБВЯЗКОЙ к каждой цели** (`$delegation`

агентов, создать и раздать задачи, исполнить, закрыть.

Артефакт пробы: пять файлов от пяти ролей (`01_architect`, `02_researcher`,

- запуск мимо `run_task.ps1` перехватывает страж `vibecoding_guard.py`

### Не лезть в работу роя — но и не подменять её одной сессией

Указание ЛПР, повторённое несколько сессий подряд: рой должен работать **автономно**,
сессия не расписывает ему роли, топологию и порядок действий. Это верно — и именно
поэтому важно отдать ему задачу штатным способом (шаги 1–3), а не ограничиться
запуском координатора. Пропуск этих шагов — не «невмешательство», а превращение роя
в одну дорогую сессию, что и происходило.

**Проверка после запуска — обязательна и делается по РЕЗУЛЬТАТУ, не по статистике
роя и не по самоотчёту.**

Критерий «Completed у воркеров должен расти» стоял здесь несколько часов
08.08.2026 и оказался НЕГОДНЫМ — снят в тот же день боевой пробой. Прогон
`air-comms` отработал полностью и успешно (пять задач, 70 → 82 теста зелёными,
реальные файлы в репозитории), а статистика при этом не сдвинулась вовсе:
`Completed = 0` у всех 42 воркеров, `Queued Tasks` как было, `Load 0.0%`.

Отсюда факт, который надо знать заранее: **воркеры `hive-mind` — записи в БД, а
не исполнители.** Работу делает Queen-сессия (Claude Code), поднятая четвёртым
шагом. Шаги 1–3 (воркеры, задача в очередь, autopilot) обязательны — без них
Queen поднимается в пустоту, что и дало `ERR-2026-000192` — но сами по себе они
работу не выполняют, и очередь роя после успешного прогона не убывает.

Поэтому проверять надо там, где результат:

```text
cd <TargetPath>
git status --short          # файлы реально изменились?
<прогон тестов проекта>     # число тестов выросло, все зелёные?
```

Статистика роя годится ровно на одно: убедиться, что шаги 1–3 отработали
(воркеры появились, задача встала в очередь). Прогрессом работы она не является.

## Одно окно — один рой на весь контур

`hive-mind spawn` не умеет исполнять в другом каталоге — состояние жёстко привязано к cwd
вызова. Поэтому рой **всегда** запускается из канонического `E:\-4-\ruflo-hive`
(`$ProjectRoot` в `run_task.ps1`), а реальный путь работы (`$TargetPath`) вписывается
**текстом в цель** — запущенная сессия сама переходит туда первым действием. Это даёт то,
что нужно контуру: одна очередь, один живой рой, не россыпь каталогов по проектам.

## Обязательная разовая настройка ПЕРЕД первым реальным запуском

`--claude` без регистрации MCP-сервера в `$ProjectRoot` тихо запускает не рой, а одну
обычную дорогую сессию без единого `mcp__claude-flow__*` инструмента — задокументированный
отказ (`005_Ruflo_Wiki`, «Пилот 04.08.2026»). Один раз для канонического каталога:

```
cd E:\-4-\ruflo-hive
claude mcp add -s project ruflo -- node "<CliPath>" mcp start
```

**Имя сервера — `ruflo`, и это не косметика.** Имя регистрации задаёт ПРЕФИКС имён
инструментов, а движок в собственном координирующем промпте (блок «CRITICAL — TOOL
PREFERENCE RULES (#1422)», 50 строк перечня) требует `mcp__ruflo__*` и запрещает
делать координацию чем-либо ещё. Пока сервер звался `claude-flow`, Queen получала
приказ на инструменты, которых у неё нет, — и наша же обвязка в том же промпте
называла другие имена. Прогон `TASK-OBS-0053` 12.08.2026 на этом встал: сессия
прочитала расхождение как признак ПОДСТАВНОГО диспетча, отказалась брать задачу и
запросила решение ЛПР (две ассистентские реплики, $0,38, ноль работы). Час назад
`TASK-OBS-0048` с тем же расхождением отработал полностью — то есть это не отказ, а
монетка на каждом прогоне.

Приёмка принимает оба префикса (`mcp__(ruflo|claude-flow)__`): старые логи и чужие
каталоги переименование не переписывает.

Затем одобрить в `~/.claude.json` → `projects["E:\-4-\ruflo-hive"].enabledMcpjsonServers`
(добавить `"ruflo"`) — либо один раз открыть интерактивную сессию в этом каталоге и
подтвердить запрос глазами. На 12.08.2026 ключа в `~/.claude.json` нет вовсе, а рой при
этом работает: реальный запуск идёт с `--dangerously-skip-permissions`, и серверы из
`.mcp.json` поднимаются без опроса. Отсюда практический вывод: переименование сервера
ничего не ломает в одобрении, но проверяется всё равно только логом прогона.

**Путь CLI в `.mcp.json` не правится руками вовсе.** `run_task.ps1` перед каждым
прогоном зовёт `ruflo_engine.py --sync-mcp`: тот приводит и путь, и имя сервера к
разрешённому `engine.json` и пишет результат в отчёт («## Движок»). Иначе рой
координируется одной версией движка, а спавнится другой — лежало 3.34.0 против 3.36.0
(ERR-2026-000226).

**`-CliPath` передавать не нужно и не следует.** Он необязателен: путь собирается по
`engine.json`. Пока параметр был обязательным, версия движка жила в СОХРАНЁННОЙ КОМАНДЕ
ЛПР — 13.08.2026 наступили второй раз: контур стоял на 3.38.8, а кнопка запускала
3.36.0, потому что номер был вписан в неё месяцем раньше. Явный `-CliPath` перекрывает
файл и годится только для сравнения версий. `run_task.ps1` проверяет присутствие в `.mcp.json` и отказывает
реальному запуску, если проверка не прошла (`exit 6`), но **не может проверить сам факт
одобрения** — это подтверждается только логом первого реального прогона
(`grep '"name":"mcp__claude-flow__' <лог>`), не самоотчётом сессии и не `claude mcp list`
(та команда показывает устаревшее состояние).

## Windows: движок ищет Claude Code юниксовым `which`, не `where`

Проверено 06.08.2026, дважды наступили. `hive-mind spawn --claude` перед запуском вызывает
`execSync('which claude')` (`@claude-flow/cli/dist/src/commands/hive-mind.js`) — юниксовую
команду, которой в Windows нет по умолчанию. Без нее движок пишет `Claude Code CLI not found
in PATH`, тихо переходит в режим "Falling back to displaying instructions" и **выходит с
кодом 0** — реальная сессия не запускается, а обёртка при этом ничем не отличает это от
настоящего успеха, если не проверять текст вывода отдельно (`run_task.ps1` теперь это делает
сам — ищет маркер деградации и возвращает `exit 7`, не `EXECUTED`).

`run_task.ps1` чинит это принудительным prepend в `$env:Path` перед вызовом:
`C:\Program Files\Git\usr\bin` (там `which.exe` от Git for Windows) и каталог с настоящим
`claude.exe` (`...\npm\node_modules\@anthropic-ai\claude-code\bin`, НЕ каталог с `.ps1`/`.cmd`
шимами — движок спавнит с `shell:false`, шимы не годятся). Если пути на конкретной машине
другие — поправить обе константы в начале скрипта, не удалять сам prepend.

## Разрешение на автономный запуск — Claude Code auto mode classifier

Отдельный от `permissions.allow` слой самого Claude Code: даже с точным разрешением на
`run_task.ps1` в `permissions.allow`, реальный запуск (`-Approval`) сессия **не может**
инициировать сама — классификатор блокирует «запуск автономного агента без надзора»
как класс действия, независимо от обёртки (проверено 05.08.2026 пятью разными способами
вызова, включая голую команду без единой строчки нашего кода — все заблокированы одинаково).

Снимается ТОЛЬКО ключом `autoMode.allow` в `~/.claude\settings.json` (уровень пользователя,
не проекта) — текстовое описание доверенного действия, не regex/путь. Правится ТОЛЬКО
человеком за консолью — попытка агента дописать себе же этот ключ **тоже блокируется**
классификатором (проверено 06.08.2026), и это ожидаемо: агент не должен сам себе выписывать
разрешение обходить проверку агента. Пока ключ не стоит — `run_task.ps1` с `-Approval`
исполняет только человек лично.

Обычный `permissions.allow` для `run_task.ps1` — держать версию кэша через wildcard
(`...\air-ruflo-bridge\*\skills\...`), не литералом: плагин обновляется, литеральная версия
в пути требует ручной правки на каждый бамп.

## Форма постановки — шесть разделов, иначе рою не подаётся

Стандарт контура: `AIR_OS/04_STANDARDS/AIR_VIBECODING.md` § 2а. Здесь он не пересказывается
вкусом, а вшит в путь: **постановка без шести разделов до роя не доходит.**

| # | Раздел | Что в нём |
|---|---|---|
| 1 | Цель как состояние | таблица фактов «что станет истинным», у каждого способ проверки и замер «истинных N из M» на сегодня |
| 2 | Механизм реализации | КАК именно, с решёнными развилками; технические развилки решает исполнитель, а не выносит ЛПР |
| 3 | Источники | что читать до проектирования, со ссылкой на место, а не по памяти |
| 4 | Результат | что появится ПРЕДМЕТНО: файлы, команды, записи |
| 5 | Метрики | было → порог; снимаются заново и кладутся файлом `metrics-<TaskId>.json` |
| 6 | Настройки прогона | какими настройками роя и ПОЧЕМУ; чем отличается от `run-config.json` — сказать прямо |

Границы и приёмка идут **сверх** шестёрки, не вместо неё.

**Седьмое обязательное — отметка согласования в шапке:**

```yaml
approved_by_lpr: 2026-08-14
```

Ставится оркестратором ТОЛЬКО после того, как разделы 1-6 выведены ЛПР в диалог и получено
явное согласие. «Сформируй задачу» разрешает написать, а не поставить: это разные
разрешения, и 14.08.2026 их смешение дало `ERR-2026-000241` — постановка ушла в очередь,
ни разу не показанная человеку.

`run_task.ps1` проверяет на этапе dry-run и наличие всех шести разделов, и эту отметку;
отказывает кодом **11**, называя недостающее. Проверка стоит именно на dry-run: развернуть
рой и на приёмке обнаружить, что мерить нечем, дороже, чем не начать.

**Чего эта отметка НЕ даёт.** Её ставит оркестратор, значит она ловит забывчивость, а не
обман: сессия, решившая проставить дату без спроса, ничем не остановлена. Тот же предел,
что у токена на почтовом сервере. Врать о нём нельзя — но забывчивость и есть основной
источник ошибок контура, а кнопка запуска этот зазор не закрывает: она предъявляет сводку
dry-run, то есть подтверждает ЗАПУСК, а не согласование текста задачи.

**Почему проверкой, а не правилом в тексте.** Правило в тексте у нас уже было — и задачи
без метрик всё равно уходили в рой; `TASK-OBS-0053` закрылся словом «сделано» при десяти
несдвинутых порогах. Текст без механизма не держит: 14.08.2026 тем же классом оказались
дефекты `ERR-2026-000236` и `ERR-2026-000237` — механизм построен, в путь не включён.

Проверяется только НАЛИЧИЕ разделов. Их содержательное качество остаётся за человеком:
машина умеет отличить отсутствующий раздел от присутствующего, но не пустую метрику от
осмысленной, и притворяться, что умеет, она не будет.

## Mandatory human gate

First run `scripts/run_task.ps1` **without** `-Approval` — mandatory `-Objective` and
`-TargetPath`. It calls `hive-mind spawn --claude -o "<цель+TargetPath>" --dry-run`, writes
the proposal (objective text, worker count, coordination prompt) to its report, then stops
with exit code 10. Claude Code is NOT launched at this stage.

Show the complete proposal/report to the human and wait for an explicit approval. Do not infer
approval from silence or from a prior request. Only after approval, re-run with the literal
`-Approval I_APPROVE_RUFLO_PLAN`. The script is the only path here that launches Claude Code
for real; it refuses to before the gate, and refuses again (`exit 6`) if MCP registration is
missing.

### Подтверждение кнопкой в Telegram — когда ЛПР не у консоли

Классификатор Claude Code не даёт сессии запустить автономного агента самой, и это
правильно. Но требование «сесть за консоль SRVLM01 и набрать команду с `-Approval`»
на практике съедало больше времени, чем сама постановка задачи: ЛПР часто работает с
планшета. Меняется КАНАЛ подтверждения, не право — каждый запуск по-прежнему
подтверждает лично ЛПР, поимённо для конкретной заявки.

```
scripts\approve_via_telegram.py create <отчёт> <файл цели> <каталог> [воркеры] [приоритет] [заголовок]
scripts\approve_listener.py --once <минут>     # ждёт решения и запускает
scripts\approve_via_telegram.py queue          # что висит нерешённым
```

Заявка хранит ПАРАМЕТРЫ, а не строку команды. Первая редакция писала в заявку готовый
вызов с `-Approval` — классификатор справедливо это заблокировал: кто угодно, получив
запись в очередь, исполнил бы произвольную команду. Слушатель собирает вызов
`run_task.ps1` из фиксированного шаблона, подставляя только цель, каталог и числа;
строки команды в этом канале не существует.

Границы: принимается нажатие только с сохранённого `chat_id`, чужие игнорируются
молча; заявка одноразовая и с TTL; токен и `chat_id` — из Windows keyring, не из
файлов и не из git. Расширение этого канала до «выполнить произвольную команду из
сообщения» превратило бы удобный гейт в удалённое исполнение кода по факту владения
токеном бота — это не настройка, а условие допустимости канала.

Сводка очереди уходит следом за заявкой: когда заявок несколько, одной кнопки мало.

#### Очередь продолжается сама — ЛПР жмёт кнопку и уходит, не дежурит у неё

Указание ЛПР 13.08.2026, дважды подтверждённое (16.08.2026): очередь существует
именно ради этого — согласовать задачу заранее и НЕ ждать момента, когда рой
освободится. Два механизма в `approve_listener.py`, оба УЖЕ РАБОТАЮТ, второй раз
объяснять их не нужно:

```
1. Нажатие кнопки ДО того, как рой освободился, — не отказ.
   _run_request() ждёт свободный замок до DEFERRED_START_LIMIT_S (3 часа) и
   запускает сама, как только рой освободится. ЛПР подтверждает ЗАРАНЕЕ, уходит,
   прогон стартует сам в нужный момент.

2. Как только текущая задача закрылась — следующая кнопка уходит АВТОМАТИЧЕСКИ.
   _push_next() вызывается в конце _run_request() для любого ТЕРМИНАЛЬНОГО
   исхода этой заявки — прогон закрылся (успехом или отказом) либо сам запуск
   не состоялся исключением; единственное НЕ терминальное — «рой занят другой
   задачей» (тот вернул бы вторую кнопку на ту же работу, строка уходит обратно
   в `queued` и ждёт своего закрытия). Отдельно звать `ruflo_queue.py push`
   руками после каждого прогона НЕ НУЖНО — если задача стоит в очереди
   `queued`, кнопка на неё придёт сама.
```

**Чего это не отменяет.** Гейт ЛПР не ослабляется ни в одной из двух веток: нажатие
всё равно требуется на каждую задачу, поимённо, с подписью — просто МОМЕНТ нажатия
и МОМЕНТ запуска больше не обязаны совпадать.

**Ручной `push`, вызванный ВРУЧНУЮ (не изнутри `_push_next`), может не выдать
кнопку по трём причинам, и «рой занят» — не единственная.** `push` сам берёт
замок роя на миг, чтобы безопасно зарезервировать строку очереди:

```
код 4  рой занят другой задачей       — не сбой; _push_next сам выдаст кнопку,
                                         как только тот прогон закроется
код 5  состояние замка не определено  — руками разобраться, это НЕ «свободно»
код 6  очередь на паузе               — снять паузу явно, автопродолжение её
                                         не обходит нарочно
```

Только код 4 не требует действия — это не сбой и не повод повторять попытку:
`_push_next()` внутри слушателя сделает то же самое сам, без участия
сессии-оркестратора, как только прогон закроется. Ручной `push` мимо
`queued`-строки, ждущей своей очереди, — лишний шаг, а не необходимый.

**Why the real run does NOT pass `--no-auto-permissions`:** the engine's own default
(`--dangerously-skip-permissions: true`) exists so a headless launch doesn't hang on an
internal prompt nobody can answer. Our external dry-run-then-explicit-approval gate already
supplies the human checkpoint that internal prompt would have provided — disabling the
engine's default here would just make the approved run hang, not make it safer.

Never say roles were actually distributed merely because Ruflo proposed them or `hive-mind
spawn` printed a worker table. Require evidence — grep the run's log for
`"name":"mcp__claude-flow__"` — before making that claim; otherwise say only “roles proposed”.
Likewise, do not report a successful run solely from Ruflo output — verify the requested
artifact/test independently.

## Daemon status without waking it

Do not call Ruflo's daemon-status command for a simple status check: it can start workers. Run `scripts/verify_daemon_state.ps1` instead. It reads the state file and compares its PID to `Get-CimInstance Win32_Process`; it reports exactly one of `confirmed`, `contradicted`, or `unverifiable`. Treat `unverifiable` as unknown, not stopped.

**`unverifiable` — не «чисто».** Отсутствие сканера, отказ запуска и таймаут дают

каждого плагина, а не отдельным плагином, на который ссылаются абсолютным путём
(`E:\-7-\air-loop\DECISION_2026-08-08_встроить_в_плагины.md`). Выключат `air-loop` —
здесь молча перестанет считаться предел кругов, и никто не скажет.

названа, гейт проверяемый, предел конечный, ЛПР показывают один раз), а не числа.
